# 多项目升级与 D015 3.0

当前 Windows 客户版、内部完整版和 CLI 共用 Shared 协议实现。不是按文件名猜设备，也不轮流发送各项目的 ENTER/擦除命令。

## 自动识别范围

|设备证据|选择|文件/边界|
|---|---|---|
|专用 Telink OTA GATT|既有 Telink Legacy/Extend|TLNK、长度、CRC trailer 预检，OTA_RESULT及重连回读|
|COM/串口透传，D170能力签名5550/schema1/协议2/包2，板型D0150320|新 D015 YMODEM|.d015，APP08002000，44KiB，包头和整包CRC32|
|D170不支持，D130明确D0150320及APP2.x|旧 D015 页协议|旧D015身份APP BIN，08001C00，47KiB|
|未提供可验证身份的旧STM32|仅用户明确手工选择旧STM32|原工程APP BIN，旧通用55KiB边界；不宣称板型已验证|
|公布未知能力/板型/分区，或D015身份与协议不一致|拒绝|不回退发送另一种升级命令|

Nordic UART service只说明传输通道，不能说明是哪一种STM32升级器。Boot的C只表示YMODEM握手，不作为板型证据。新D015能力窗口在APP和空闲Boot都可读。无身份的旧D015 Boot不能自动恢复：须先解决可靠身份/工厂维护路径，不绕过D015镜像板型门禁。

未来项目若实现同类只读能力描述，仍须在当前支持表中明确板型、地址、容量、包格式并通过测试后才放行；不增加通配板型或插件框架。完全未知协议无法安全自动兼容。

## 使用

1. 正常设备连接COM或BLE，选择固件，OTA页保持Auto并开始。连接目标固定为用户选定的COM/MAC，不扫描换设备。默认19200 8N1必须与硬件一致。
2. 新D015中断恢复：选择串口/COM，勾选“D015串口恢复”，无需先连接APP，选择配套.d015后开始。工具保持原COM，用250ms只读探测捕获500ms上电窗口，最长35秒；可在等待时重新给设备上电。断线会话30秒无实际进展退出，再冷却1秒；若设备安全关闭失败需排除硬件原因并复位。
3. 短时坏包/丢ACK由YMODEM按块号有限重试；复位/取消/连续失败后从文件头重发。进度不是成功证据。
4. 新D015发送完成后重建同一设备链路，核对板型、固件版本、整包CRC32、载荷长度及实时BMS数据。只有这些匹配才完成100%。最终ACK超时或最终写入发生I/O断线均先核对APP结果，不自动重擦。共享发送器返回同一份身份、实时数据和Build ID读回，UI/CLI不重复执行升级成功判断；WPF完成后点击连接恢复实时监控。
5. 旧隐式页协议不能盲重发页，ACK超时停止；Telink路径保留现有结果判定。需要的旧手动选择应由维护者先核对工程起址，不用作D015身份绕过。

APP→Boot及Boot→APP复位可能重启串口蓝牙桥，客户端重新连接原设备。BLE按20字节分片并留UART排空时间；真正桥接断连/吞吐仍须板测。取消是停止本次升级，不能恢复已擦除的旧APP。

D015 3.0首次须通过产线/调试器安装配套新Boot+APP，旧Boot不能在线迁移为新Boot；参数/SOC地址改变，需备份/恢复。新协议只有CRC完整性，没有签名、防降级或自动回滚。

## BMS功能与版本边界

沿用当前实时电压/电流/温度/SOC、61001缺串、软硬件保护参数读写、AFE分片提交与回读、线性电流校准、SN、容量、均衡/休眠参数、事件日志和诊断。内部版包含完整SOC/OCV与工厂功能，客户版保持既有编辑权限边界并增加升级/恢复入口。Android未增加串口升级UI。

## 验证与发布

- `test-d015-upgrade.ps1 -FirmwareReceiver <实际C接收器update_test.exe>`：生产C互通，坏CRC、丢数据/最终ACK、取消、复位重传、只读识别、双向复位重连和最终精确回读。
- `test-d015-interop.ps1`：两版程序集对真实BMS C模块，参数/硬件使能/校准/SN/实时/61001，并模拟旧D015的识别及延后ENTER ACK。
- `test-ota-protocol.ps1`：原Telink预检和协议回归。
- `test-business-parameters-ui.ps1`：两版参数页面/只读边界、23项实际D015基本参数、两版升级入口。
- 客户WPF、内部WPF、CLI、Core Release构建；客户版仅保留既存CS0649，其他0警告。无真实串口/BLE/电池板验收。

本轮发布标签 `d015-v3-20261101`，正式EXE在各项目publish目录；源码Git提交与SHA256由build-release.ps1打印，并写入发布清单。不生成任何固件BIN/HEX。

## 2026-11-01 恢复与确认修复

- D170 mode：0 APP，1 安全Boot，2 安全失败/禁止擦写，3 可请求进入的上电窗口。mode2拒绝ENTER；旧版3.0 Boot的mode2含义不明确，也按禁止处理，不绕过关断门禁。正常APP和mode1继续支持。
- Modbus接收按当前请求地址/功能匹配帧头，允许Boot的C前缀及逐字节分片；接收缓存有界，CRC错误不当作旧协议支持。普通自动识别只对明确不支持(异常码1/2)或无应答继续只读旧身份查询；断线/坏CRC不授权旧写命令。
- 新包只使用新D015只读能力探测，不先读普通APP快照；ENTER等待6秒覆盖APP的4秒准备期限。ENTER后重连原端点并重新核对能力、板型、地址、容量及mode1；未知能力直接拒绝。
- EOT完成不等于最终提交。最终空块尝试前取消发送CAN CAN；尝试之后取消/断线可能已提交，显示结果待确认。最终ACK不确定时用精确APP读回解决，读取失败也不能宣称设备未写入。
- 未增加协议插件、多层调度或第二套OTA判定。新增只读恢复入口用于真实的启动窗口；D015UpgradeReadback承载UI/CLI实际需要的唯一确认结果。
- 本轮回归加入C前缀/逐字节应答、未知能力、I/O不降级、mode2无写、实际C的mode3进入、重连身份不符、EOT取消和最终写入I/O异常。另验证Telink原协议、AFE分片以及客户/内部BMS实际C互通。
- 本轮发布标签 `d015-v3-20261101-recovery`，不生成固件BIN/HEX；实板串口/BLE、断电、Gate仍待验收。
