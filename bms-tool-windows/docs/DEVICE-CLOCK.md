# D015 板载时间与自动校时

两版Windows上位机共用 `Shared/BmsClient.DeviceClock.cs` 和 `MainWindow.DeviceClock.cs`。
首页底部与设备信息页显示板载时间，每5秒读取一次真实日历，不在电脑端自行推算板载秒数。
页面时间按电脑本地时区显示，末尾显示UTC偏移；板内日历始终为UTC，2000～2099年。

连接并识别D015后，以及后续正常轮询中，时间未同步或与电脑误差**严格超过300秒**才写入校时。
正负300秒本身均不写。写入后再次读取，允许通信耗时及整秒截断造成的10秒验证误差；
验证不通过不报告成功。所有校时使用现有Modbus事务及同一个transport，不新开串口。

读取/校时失败时显示未知，30秒后重试，后续电池监控继续。写入生效但ACK丢失时，
重试先读当前时间，已经正确则不重复写。连续8秒无成功业务响应或更换连接时两处时间一起清空。
其他产品不发送时间请求；旧D015返回异常1/2或无对应签名/版本时，本次连接不再探测，更不会写入。

## 协议

03一次读 `2E70..2E76`，共7字，响应19字节；10一次写 `2E73..2E76`，共4字，请求17字节。
二者均适用于MTU23。每字高字节在线上在前。

|地址|内容|
|---|---|
|2E70|签名5254|
|2E71|版本1|
|2E72|位0 RTC可用；位1整组UTC日历已校时；0不可用、1未校时、3已校时|
|2E73|完整年份2000～2099|
|2E74|高字节月，低字节日|
|2E75|高字节小时，低字节分钟|
|2E76|秒0～59，高字节必须0|

无效时间的四个日历字为0。必须写完整四字，单字及部分写入被拒绝；无Flash写入、无需参数解锁。

## 固件边界

新固件深睡保留RTC/LSI计时，屏蔽RTC闹钟、EXTI17和IRQ，只有PA0充电唤醒。
完全断电丢失日历，首次重连重新校时；不能通过保存Flash知道断电持续了多久。
内部LSI未做逐板频率校准，离线上下电/升级间隙和温漂仍影响精度；自动校时依赖电脑时间正确，
不访问互联网、不修改电脑时间，也不把现有事件记录的运行毫秒字段改为日期。

## 验证

`test-device-clock.ps1` 对两版实际程序集测试UTC、300秒边界、首次校时、正负漂移、非法日历、RTC不可用、
旧固件异常1/2、丢ACK与回读失败；可传 `-FirmwareHarness` 运行实际D015 C模块协议联测。
`test-main-window-experience.ps1` 验证两处时间控件与断线清空；`test-communication-layout.ps1` 检查小屏布局。
客户WPF、内部WPF、CLI与Core均须编译通过；这些证据不替代实板长时间走时/功耗/PA0唤醒测试。

发布：`build-release.ps1 -ReleaseTag 20261103-device-clock -OutputRoot <正式交付目录>`。
输出客户版、内部版、CLI自包含EXE；编译中间文件仍在用户临时区。
