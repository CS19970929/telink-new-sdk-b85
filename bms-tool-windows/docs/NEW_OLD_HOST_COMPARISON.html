1. 结论

当前 C060 的连接、实时监控、保护参数和常规参数，优先使用新版。 新版已经针对实际协议修正身份读取、实时窗口、整组保存、校准符号编码和失败反馈，并提供自动识别及旧项目手动选择。

新版还不是旧版所有功能的完整替代品。 旧版的多站地址管理、串机汇总、旧Excel参数模板、逐通道两点校准操作流程、模块AT配置等，没有全部按原样迁移。新版的一些诊断、AFE编辑和校准功能属于其他固件，不能直接算成C060已支持。

当前C060新Boot升级，两套Windows上位机都不能直接视为已经配套。 旧版发送FFFD/FFFE/FFFF；新版虽有D015 YMODEM，但其升级识别仍固定D015板号和容量。C060当前工程已有独立新版升级工具，需要按C060合同另外接入Windows上位机。

4. 当前C060：新版本具体改善了什么

4.1 连接和实时

截图报错对应读取C012/16，而C060身份需要C002/48整体拆分。此前新版的D120/11还会越界。当前新版已针对C060使用正确窗口；D170只用于它实际声明的能力，旧固件仍可通过已有身份/结构识别，或由用户明确手动选择参数协议。

旧版直接使用原传统窗口，因此没有同一C012握手问题。但它没有统一的设备识别或能力隔离，不能由“以前能连接”推导它对新版全部行为都配套。

4.2 保护及批量写入

旧版一键写每步只等约1s，设备90异常应答也可能没有结束全局等待，最终出现同一句“全部参数写入异常”。此前生产函数模型已复现“正常提交尚未结束，ACK迟到而被误判超时”的机制；没有实际抓包就不能认定每次现场都只有这一种根因。

新版保护与常规参数各自先读设备当前值，合并修改、检查完整候选及长度，再按规定整组发送。保护每组5字，19字节RTU请求，MTU23可承载；容量/循环/端点每组4字，17字节请求。错误会定位到组和回读阶段，不自动重发。

均衡2300，8字fresh read保留其余字段；关闭压差标为兼容项
CBC及SOC表2308，8字档位规格化/有效值预览；不把参数回读等同AFE确认

跨组保存仍可能部分成功。提交后ACK、回读一致和Flash寿命/掉电可靠性还取决于当前固件与硬件，不能因换了上位机就承诺永不超时或所有保护实板生效。

4.3 BLE长度与旧模板

旧工具主要走COM，不处理BLE ATT载荷限制。新版连接BLE后必须核对整组请求长度：8字需MTU≥28，16字生产信息需≥44，24字热冷需≥60。MTU不足时整个本次常规批量在预检阶段停止，保留连接与可用短组写；当前没有对未验证的模块强行启用普通长帧分片。

旧.xls的121行是固定UI模板，可能含尚未发送的编辑值。新JSON来源是读回capture；导入只载入候选，保护和常规参数仍分开确认保存。文件不互通不是单位自动换算已经完成，不能仅改后缀或照行号填入新页面。

6. 两端共同受固件能力限制的功能

  • 完整分段电流校准：C060现有3000/3050只返回部分点及点数，不能还原写接口所需全部K/B/端点。新版读了摘要，也不能称无损备份。
  • BQ76930硬件保护：旧2400/24项和新2500/35项、0x42分别属于不同合同；C060没有直接匹配完整编辑器。CBC参数组存在，不代表已经确认实际AFE寄存器。
  • SOC表、铜损、RTC写入和部分控制/清除：当前C060仍有旧空实现或只读/保留字段。两版都不能把ACK当作业务完成。
  • 热冷/旧Sleep：当前无热冷运行控制，新的RTC与预充策略使用固件宏。UI可保存兼容字段，不代表策略改变。
  • 事件时间：新版正确识别170与171，但C060中间时间编码及STOP时间源问题仍在；“EEPROM错误”事件旧标签也仍保留，当前实际存储为Flash。
  • MOS/诊断/工厂测试：新平台已有针对其他产品的扩展，不等于C060实现2F10、2A00、0x41或0x42。可用通信应继续保留，对缺失功能逐项说明。
  • 当前C060新升级：固件使用3500=B007、D170/D17C、C0600020板号、51KiB及.c060格式包；旧FFFD已明确拒绝。新版Windows升级能力解析仍只认D015。C060仓库自己的tools/c060_upgrade.py是另一入口，不等于Windows页面已完成接入。
