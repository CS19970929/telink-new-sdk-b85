# 运行阶段调试日志

固件主开发分支为 `codex-bms-monorepo`；Windows 上位机仍在
`feature/windows-afe-hw-protection-editor-v2` 的 `bms-tool-windows/` 维护。
四产品共享 `bms/core/bms_debug_log.c`，产品 sources.txt 引用同一文件。

## 使用

默认 `BMS_DEBUG_LOG_ENABLE=0`。开发时用编译参数启用，避免把调试配置提交为量产默认值：

```powershell
$env:BMS_BUILD_ROOT = "$env:LOCALAPPDATA/CodexTemp/bms-runtime-log/debug"
$env:EXTRA_DEFINES = '-DBMS_DEBUG_LOG_ENABLE=1 -DBMS_DEBUG_LOG_LEVEL=4'
python bms_tools/bms.py --all-products link --jobs 4
python bms_tools/bms.py --all-products resources
```

`link` 只生成 ELF/MAP/LST，不生成 BIN。本次未生成镜像或烧录。
等级 1=ERROR、2=WARN、3=INFO、4=DEBUG，包含低于等于配置值的等级。
`BMS_DEBUG_LOG_MODULE_MASK` 默认 `0x01FF`，bit0..8 分别为系统、AFE/采样、
保护/MOS、SOC、通信、低功耗、存储、均衡/功能、OTA。例如 `0x0026` 选择 AFE、保护、低功耗。
INFO 适合观察状态变化；DEBUG 另外记录周期采样、SOC 决策/积分、单体范围和通信。
模块、等级均在编译时筛选；关闭/过滤记录时不计算记录参数。

量产必须去掉 EXTRA_DEFINES 中的调试开关，并使用仓库既有 `--production` 门禁。
同时指定 `BMS_PRODUCTION_BUILD=1` 与 `BMS_DEBUG_LOG_ENABLE=1` 将编译报错。
关闭后无日志环形缓存和日志写入函数；保留只读能力窗口，供上位机显示“日志已关闭”。
量产门禁还要求干净提交、D008 明确 profile 和不少于 8 KiB 的 Flash 余量，关闭日志本身不等于通过所有发布条件。

连接新版 Windows 工具的串口或 BLE 后，打开“运行日志”，点击“读取运行日志”。
支持等级/模块过滤、停止、清空显示、导出文本及可选每秒采集，最多保留 2000 条。
自动采集默认关闭；过滤仅改变显示，不改变固件记录等级。详细界面说明见上位机分支
`bms-tool-windows/docs/RUNTIME_LOG.md`。

## 与协议、低功耗和 Flash 的关系

这是 RAM 运行日志，与 `bms_event_log` 的 Flash 历史事件独立，不改变持久布局、参数版本或历史事件策略。
记录固定二进制字段，固件无 printf、动态内存、字符串格式化、额外 DMA 发送或等待。
主循环拥有记录缓存；SDK suspend exit 回调仅递增一个 volatile 32-bit 计数，主循环每秒汇总。
UART IRQ 中不记录日志。BLE 接收入口延续 SDK 主循环分发路径。

串口和 BLE 通过既有 Modbus 03 请求读取新增只读窗口。既有寄存器、帧格式、CRC、波特率、
RS485 DE 控制和 UART DMA 完成门禁保持原实现。不会把裸文本插进正常应答，也不新增主动推送通道。
因此普通串口文本终端不会直接显示日志，需使用上位机或按下述寄存器协议读取。
正常日志读取不生成自身通信记录，避免查询反复填满缓存；非法请求、CRC 错误仍可记录。
06/10 写入及跨入日志窗口被拒绝；广播不应答。

日志积压不阻止 suspend，不增加睡眠入口、唤醒源或 flush 等待。普通 suspend 保留 RAM；
deep sleep、reset、掉电会清除日志，成功深睡前的最后记录可能来不及读取，这是明确取舍。
调试记录会增加少量 CPU 时间；主动串口/BLE 读取会延长通信活跃时间，使用原有通信休眠互锁，
可能减少 suspend 时长。测待机功耗应停止上位机自动采集，并分别比较日志开/关的实板波形。
不能将“没有新增日志阻断条件”理解为“开启调试后功耗和时序完全不变”。

Windows 每次最多读取 4 条（40 个寄存器、85 字节 RTU 响应），复用当前 BLE 分片、
请求锁和超时机制。OTA 启动会先取消并等待读取退出，超时则拒绝启动此次 OTA，防止共用传输交错。
无连接不自动采集；读取失败会停自动采集，不忙循环重试。

## 寄存器协议 v1

地址范围 `[0x3000, 0x3290)`，Modbus 03，只读。
每个 word 大端；每个 u32 **高 word 在前**，与旧诊断窗口的 u32 排列不能混用。

| Header word 偏移 | 内容 |
| --- | --- |
| 0 / 1 | magic `0x4C47` / schema `1` |
| 2 / 3 / 4 | enabled / 容量 64 / 每记录 10 words |
| 5 | 当前有效记录数（最多 64） |
| 6..7 | 下一条 sequence，u32 自然回绕 |
| 8..9 | 缓冲满后累计覆盖数，u32 饱和 |
| 10..11 | 初始化时 32K tick |
| 12..13 | BMS_DIAG_BUILD_ID |
| 14 / 15 | 编译等级 / 模块 mask；关闭时为 0 |

记录槽位从 `0x3010` 起。sequence 从 0 开始，物理槽号为 `sequence % 64`。
每记录：sequence(u32)、tick32k(u32)、level高8位/module低8位(u16)、event(u16)、arg0(u32)、arg1(u32)。
环形数组本体 1280 字节，不消费式读取；多个客户端各自维护 cursor。
32K tick 约 37.3 小时回绕，是设备原始计时，不是墙钟时间或累计运行时长。

读取 header 后按序号请求物理槽位；跨请求会有新事件覆盖旧槽，必须逐条校验 sequence。
Windows 跳过被覆盖槽并报告缺失；读取结束再核对启动 tick、build 和序号方向，失败不提交 cursor。
“RAM累计覆盖”不是该客户端丢失数，“本次缺失”才表示该次采集没拿到的记录。
重连重建 cursor。启动 tick 不是唯一 boot ID，同 build 极短时间重启且 tick/序号恰好碰撞时不能保证识别；
怀疑发生这种情况时断开重连。序号比较假设相邻采集间小于 2^31 条事件。

## 记录点与字段

事件 1..13 复用 `bms_diag.h` 的启动、存储、参数、MOS 请求/驱动缓存、保护、AFE资格、PM状态。
MOS 请求/缓存不是物理 Gate 反馈，日志不声称闭环硬件成功。
详细事件以 `bms_debug_log.h` 编号和对应 BMS_LOG 调用为字段真源，上位机保留原始参数供追溯。

| 事件 | 覆盖内容 |
| --- | --- |
| 32..34 | 有效采样/带符号 mA、SOC 决策前后值/原因/静置秒、积分间隔与 As×10 增量 |
| 35..37 | UART/BLE 帧长度/功能码/响应长度，CRC计算值与接收值 |
| 40..45 | BLE入队失败偏移、连接变化、深睡尝试/中止/返回、OTA工作状态 |
| 46..51 | 均衡 mask/失败、各级保护位变化、Modbus异常、单体min/max、SOC状态 |
| 53..58 | AFE状态变化、suspend退出次数、SH事务失败/重试耗尽/恢复、UART TX busy |

38、39、52 保留，不在当前 monorepo 产生。SH 事务日志仅对应 SH 后端；D008 通过公共诊断记录 AFE 状态。
有界缓存采用覆盖最旧记录策略，不为 ERROR 保留独立区。DEBUG 高频模式应持续采集或缩小模块范围；
日志并非永久完整轨迹，也不逐字节记录 AFE 寄存器传输。
