## 按安全影响排序的发现

### DVC-01 / P1：恢复逻辑把 R1.CST 当作 R6.DSGF，可能误清放电故障并重新开 MOS

依据：RM p6 的 R1 bit1 是 CST[1]；RM p7–8 的 R6 bit1 才是 DSGF。`bms/afe/dvc1124/dvc1124.c:1603` 将 R1 赋给 `s_snapshot.status`，而 `dvc1124_bms.c:249` 用 `DVC1124_CC2_DSGF_MASK` 在该字段上检查 driver off。

证据：原样恢复函数 host 注入 R1.CST=0、实际 R6.DSGF=1、PB1 load_removed=1，经 200ms，预期仍锁定，实际 discharge lock=0；R1.CST=2、实际 R6.DSGF=0 则相反，预期可恢复实际 lock=1。HW_PROTECT=0/1 均复现。`tests/fixtures/d008_current_recovery.c:21` 人工把 DSGF 填入 snapshot.status，掩盖了真实采集/消费边界不一致。现有测试通过不构成该逻辑正确依据。

影响：PB1 高电平和错误字段组合可被当成物理释放条件，故障负载仍接入时解除 OCD/SC 锁定并请求开 MOS；另一 CST 值又导致正常负载移除后不恢复。

建议：snapshot 独立保存 R6 FET flags，恢复逻辑只使用该字段；从完整原始寄存器 frame 运行真实解码→恢复链。不得以改测试填充方式作为修复。

验证：host 覆盖 CST=0..6 与 DSGF=0/1 正交组合、PB1 边沿抖动、200ms边界与失败分支；实板观察 AFE flag、GP6、DO、MOS Vgs 和负载电流，确认未恢复负载始终锁定。证据 `recovery_results.txt`、`independent_host.py`。

### DVC-02 / P1：CRC 正确的旧 ADC 值被发布为新采样，影响保护、启动与断线检查

依据：DS p13–15，CC2 固定 256ms；每次 CC2/VADC 完成分别设置 CC2F/VADF；RM p6 明确这些位为 RC。当前默认 VASM=1、VAMP=0，每 1 个 CC2 周期测一次电压。`dvc1124_bms.c:22` 应用采样周期为 200ms。

代码：`dvc1124.c:1591` 只要求 R0..R4C 读取/CRC 成功，`:1601` 无条件 valid=1，`:1703` 更新 host 当前 tick，`:1704` 自增 generation；未建立 VADF/CC2F 与成功数据的新鲜性关系。270ms boot-zero 等待采用时间假设（`:306`、`:428`），并未观察转换完成事件；原厂未给 CAMZ 最长完成时间。

证据：原样 `DVC1124_App_AFEGet` host 只返回固定 ADC 数据、R1.VADF=CC2F=0：第一次 generation=1 valid=1 tick=100；第二次同样无完成事件 generation=2 valid=1 tick=6500。原厂事件表不支持把每次总线成功解释成每次转换完成。证据 `freshness_host.py`、`freshness_results.txt`。本反例 stub 无其它 RC 消费者，因此不存在“已由别处消费完成位”的解释。

影响：启动所需连续好帧、恢复、电流/电压软件滤波、SOC 等可能使用重复数据却认为新鲜。`DVC1124_OpenWirePoll`（`:1366`）把 generation 变化和 200ms当作受刺激新测量资格，可能抓到 COW 开始前的旧 VADC，提前关闭 COW，断线漏报属于实际芯片相位/RC时序待验证风险。

建议：规定单一 RC 事件所有者，分开 CC2 与电压的新鲜 generation/tick；只有对应完成且传输成功才发布“新样本”。失败重试读过 R1 的 RC 副作用也必须被保留。Openwire 必须确认 COW 开始后完成的 VADC，不能由读取次数证明。询问原厂 ADC 多字节快照原子性和 CAMZ 完成界限。

验证：真实生产 TU 输入带/不带完成事件的连续帧、CRC 在 R1 后失败的重试、不同 VADC/CC2相位；实板扫采样相位、COW 和 NTC RC 延迟、断线注入；不能仅确认所有寄存器数据可读。

### DVC-03 / P1：硬件 OCC 仅等待 30 秒及软件故障清除就解除，不要求充电器物理释放

依据：DS p18 规定 OCC1/2 告警锁存及 MCU 清零/关闭 enable 等解除方式，未规定 MCU 何时可以认为外部充电故障已消失。项目安全需求明确 SC/OCD/OCC 不能仅凭关 MOS 后 0A 恢复。

代码：`dvc1124_bms.c:29` `DVC_OCC_RECOVERY_TICKS`=30×32000；`:240`–`:242` `charge && !sw_charge && elapsed>=30s`，无 charger removed、reverse、qualified AFE driver/window 等物理条件。关充电 MOS 后电流为零可让软件 OCC 消失，计时后清硬件锁存，再请求开 MOS。

证据：抽取当前生产恢复函数，硬 OCC 锁存保持、无物理释放证据、软件fault降为0、经过30s，预期charge lock=1，实际=0；HW0/1 均复现。`recovery_results.txt`。

影响：未移除故障充电器可能周期性再次导通/保护重触发。不是原厂要求必须保持30s，也不能把“MCU可以清告警”解释成“MCU应按固定时间清”。

建议：由产品签核恢复证据、阈值/去抖/ownership；硬件已自动因反向电流开启的通路和 MCU 清 latch 要分别验证。没有选定产品策略前本轮不修改恢复行为。

验证：持续故障充电器、真实拔插、充放电反向、MOS漏电/电流测量死区、MCU reset/watchdog场景；测量实际 Vgs 和充电电流，不能只观察软件flag。

### DVC-04 / P1/P2：允许低于硬件最小值的 OC 请求，实际阈值向上提高

依据：RM p18–20，OC1 非零最小 0.25mV，OC2=(code+1)×4mV 最小4mV。200µΩ时分别最小1.25A和20A。

代码：`bms/core/bms_afe_hw_profile.c:289`–`:296`只检查上限；`dvc1124.c:616`–`:637` OC1 code0强行1；`:641`–`:664` OC2 index0强行1。默认 `param.h:98`–`:105` 的OC2请求15A实际成为20A；请求1A仍可接受并转成20A，不满足代码“floor不超过请求”原则。不是单纯向下量化。当前三profile的原函数host还验证：1A OCD2 请求 `validate=1`，effective=20A；0ms OCD2延迟请求 `validate=1`，effective=4ms（原厂最小4ms）。电压延迟低于200ms/OC1低于8ms也仅检查上限，属于同类最小可表达范围遗漏；当前默认100ms OC1向下到96ms是正常量化。

影响：使用者配置较低保护电流，硬件实际允许更高电流；可由 effective readback 察觉，但 commit success 不代表请求得到满足。

建议：验证启用非零最小可表达范围，拒绝不满足保护约束的请求，或明确展示并要求已签核的 effective；默认15A是否可接受必须由产品电芯/线路/MOS依据确定。

验证：原厂公式生成边界向量，0/最小以下/最小/每档边界/上限；请求、持久化、最终寄存器和 effective 成对检查，实板电流源+示波器测trip。参数存储/OTA整体证据由主报告补充。

### DVC-05 / P1 安全签核缺口：生产默认独立硬 SCD 关闭

依据：DS p18–19 独立 SCD 比较器，阈值10..630mV、延迟0..1992µs；OC2最短4ms，不能自动视为等价短路保护。
