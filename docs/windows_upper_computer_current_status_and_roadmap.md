# Windows BMS 上位机现状、功能细节与后续路线图

## 1. 文档目的与基线

本文是当前 Windows 上位机的维护、交接、测试和后续模板化改造基线。内容以仓库 `codex-mos-protection-coordination` 分支源码为准，生成日期为 2026-09-08。文中将“已实现”“部分支持/未实板验证”和“规划项”明确区分，不把设计目标当成现成功能。

仓库和工程位置：

```text
仓库：D:\\telink\\tc_ble_single_sdk-V3.4.2.8_Patch_0001 (1)\\tc_ble_single_sdk-V3.4.2.8_Patch_0001 (1)
上位机根目录：bms-tool-windows\\
客户版：bms-tool-windows\\BmsTool.Windows\\
完整版：bms-tool-windows\\BmsFactoryTest.Windows\\
公共代码：bms-tool-windows\\Shared\\
```

两个程序都是 WPF、x64、self-contained 发布目标：

| 程序 | 用途 | 当前边界 |
|---|---|---|
| `BmsTool.Windows` | 客户日常使用 | 实时监控、设备信息、事件日志、长期监控；软件保护/BMS 参数和 OTA 默认隐藏，输入 `hs456` 后显示 |
| `BmsFactoryTest.Windows` | 研发、调试、产线 | 在客户版能力之上增加 AFE 硬件保护、专业调试、出厂测试、Flash 寿命测试；无密码门槛 |

## 2. 当前整体架构

上位机采用“传输层—协议层—设备服务—页面/测试编排”的分层：

```text
BLE 广播 / COM 端口
        ↓
IBmsTransport
  ├─ BmsBleTransport：Nordic UART GATT、通知、MTU、重连
  └─ BmsSerialTransport：COM、可配置波特率、8N1、分片接收
        ↓
ModbusRtu：组帧、CRC16、响应长度、异常帧
        ↓
BmsClient：探测、身份、实时数据、参数、日志、休眠、Factory Session
        ↓
MainWindow：实时界面、参数页、日志页、OTA
FactoryTestEngine：完整/单项 Factory Session 测试编排
```

完整版通过 `.csproj` 链接复用客户版的 `BmsClient`、`ModbusRtu`、BLE/串口传输和 OTA 核心；公共动态页面放在 `Shared`。这样普通协议修复通常只需要改一份，但 SH367309 AFE 参数目录和页面仍在完整版中单独维护。

## 3. 用户界面功能清单

### 3.1 实时监控页（两版都有）

连接成功后，上位机以约 1 秒周期读取电池快照。页面展示：

- 单体电压：最多 32 个协议槽位，显示有效串数、最大/最小/平均电压、最大压差和最大/最小串号；
- 32 个单体卡片：保持原协议串号，不因中间缺串而压缩编号；
- 总压、电流、SOC、SOH；
- 当前容量、满充容量、出厂容量、循环次数；
- 最高温度、最低温度、MOS 温度；
- 充电/放电 MOS、预充、继电器、加热、制冷、均衡、AFE、系统状态等灯态；
- L1/L2/L3 软件保护文本和原始故障字；
- 硬件版本、软件版本、BMS 序列号和通信状态。

电压规则已经固定：固件传输 `61001` 表示该槽位不存在，不是 61.001 V。上位机只把非 `61001` 的槽位纳入有效串数、平均值、极值和压差统计，且保留原始串号。

断连或自动重连期间，客户主页面保留最后一次有效数据显示，不用零值覆盖；通信诊断继续写入日志。

### 3.2 通信设置

通信区域支持两种入口：

| 模式 | 当前行为 |
|---|---|
| BLE | 主动扫描、显示设备名/MAC/RSSI，连接 Nordic UART service，启用 RX 通知 |
| 串口 | 枚举 COM，选择或输入波特率，连接后复用相同 Modbus 和页面逻辑 |

BLE 扫描优先显示广播名以 `BT_` 或 `BT-` 开头的设备。无名称设备不会全部显示，而是先确认其提供 Nordic UART service，兼容 STM32 串口蓝牙模块进入 IAP 时没有本地名称的情况。

BLE 使用 Nordic UART UUID：

```text
Service  6E400001-B5A3-F393-E0A9-E50E24DCCA9E
TX       6E400002-B5A3-F393-E0A9-E50E24DCCA9E
RX       6E400003-B5A3-F393-E0A9-E50E24DCCA9E
```

串口默认是 `19200 baud、8 data bits、No parity、1 stop bit、No hardware flow control`。波特率不是固件协议中的动态字段：上位机虽然允许输入其它值，但 BMS SCI、串口蓝牙模块和上位机必须一致。

### 3.3 设备信息 / 蓝牙名

设备信息页读取：

- BMS MAC：寄存器 `0x0000`，不可用时回退 BLE 连接地址；
- 蓝牙名：寄存器 `0x0100`，不可用时回退广播名；
- 序列号：`0xC002`；
- 硬件版本：`0xC012`；
- 软件版本：`0xC022`。

蓝牙名修改要求填写后缀，程序补齐 `BT_` 前缀，只允许 ASCII 字母、数字、下划线和短横线；当前 BLE 请求的后缀上限为 10 字节。外置串口蓝牙模块可能不提供 BMS MAC/名称寄存器，此时不影响实时数据读取。

### 3.4 软件保护 / BMS 参数

客户版该页默认隐藏，输入 `hs456` 后显示；完整版直接显示。页面支持：

- 读取 65 个正式软件保护参数：`0x2100..0x2140`；
- 按行编辑保护阈值、恢复值和滤波参数；
- 写入选中项或全部修改项；
- MCU 软件保护参数写入后回读校验；
- SOC 写入：`0x1005`，写入后读取电池快照校验；
- 循环次数写入：`0x2319`，写入后读取电池快照校验。

写操作会停止轮询，等待通信空闲，再执行应答和回读；失败时不会自动盲目重发。`hs456` 只是客户版 UI 访问控制，不能替代固件权限、写保护或量产安全机制。

### 3.5 3520 保护参数页

两版均动态增加“3520 保护参数”页。客户版跟随高级功能访问状态，完整版直接可用。页面分为：

- MCU 软件保护；
- AFE 硬件保护。

读取时先通过 `0x2500` 识别 SH3673520 型号/版本，再读取对应的 24/32 字参数块。模式、同口/分口、看门狗、SPI 类型、分流器参数和配置校验状态提供只读显示。保存软件和硬件参数分开进行，硬件保存后还要检查 AFE 配置已应用。

3520 整组 BLE 写入需要足够 MTU（当前代码要求请求可以容纳约 57 字节数据，实际需 MTU 至少 60）；MTU 不满足时应使用直连串口或具备更大 MTU 的桥接链路。未识别为 3520 的设备不能按 3520 字段解释。

详细字段和物理编解码见 [3520 参数说明](../bms-tool-windows/docs/3520_parameters.md)。

### 3.6 AFE 硬件保护页（完整版）

完整版动态增加“AFE硬件保护”页，当前针对 SH367309/D3PRO 参数模型。支持读取 24 个寄存器、编辑合法范围/步进/离散档位，并只写发生变化的参数组。当前覆盖：

- 单体过压/欠压阈值、恢复值、延时；
- 充电过流、放电过流 1/2 阈值和延时；
- 充放电高低温阈值和恢复值；
- 短路电流和短路延时。

地址基线为 `0x2400..0x2417`。保存后要求 ACK、回读一致；固件随后异步更新 AFE EEPROM。此页的写入明确限制为 BLE，直连串口只能作为公共读取/其它公共功能链路，不能把 BLE 专用硬件参数写入通道误用到串口。

### 3.7 事件日志

两版均支持读取设备事件日志，并自动识别设备容量：

- 从 `0xC008` 开始，每条事件占 1 个寄存器；高字节是事件类型，低字节是与上一条事件的间隔编码；
- 先读前 100 条，再读第二页；只有第二页明确返回 `0x03` 功能、异常码 `0x01` 的地址非法，才判定为 100 条；
- 第二页及后续页均成功时，继续读取 `C008/C06C/C0D0/C134/C198` 五页，判定为 500 条；
- 超时、CRC 错误、短响应或其它异常不降级为 100 条；
- 读取期间暂停轮询并防止重复点击；
- 当前界面把已知事件映射为中文，未知事件保留编号。

完整版额外支持“删除设备日志”：发送 `0x06`、寄存器 `0x1007`、值 `0x0001`。只有收到合法 ACK 才清空界面，失败时保留旧列表并要求重新读取核实。客户版没有删除入口。

当前协议没有冻结日志快照；多页读取期间如果设备产生新事件，页间可能存在时间点不一致。

### 3.8 长期监控与 Excel 导出

两版实时监控页都增加长期监控工具栏，间隔可选 1/5/10/30/60 秒。记录来自上位机成功读取的有效快照，包含：

- 时间、蓝牙名、总压、电流、SOC、SOH、工作状态；
- 容量、循环次数、最高/最低/MOS 温度；
- 最大/最小单体和压差；
- MOS、加热、制冷、均衡状态；
- L1/L2/L3 告警；
- 硬件版本、软件版本、序列号；
- 每个有效单体的电压列。

记录只保存在当前进程内，停止后可导出 `.xlsx`。断连期间不写入伪造或清零数据。当前最多保存约 1,000,000 条内存记录，尚无数据库持久化和断点续采功能。

### 3.9 设备休眠

两版实时监控页提供休眠按钮。确认后发送 `0x06`、寄存器 `0x1102`、值 `0x000A`。收到合法 ACK 只表示 BMS 接受请求；上位机随后停止轮询、取消自动重连、主动断开，提示用户按板上唤醒后重新连接。超时不当作成功，也不自动重发。

### 3.10 OTA 升级

OTA 页面客户版默认隐藏，完整版直接显示。目标可选 Auto、Telink 专用 OTA、STM32 串口 IAP；传输模式支持 Auto、Legacy Fast、Extend 64B。

| 目标 | 识别/链路 | 当前流程 |
|---|---|---|
| Telink | 发现 Telink OTA service | START → DATA → END，按设备能力选择传输模式，等待 OTA 结果 |
| STM32 + 串口蓝牙 | Nordic UART GATT | `0xFFFD` 进入 IAP，等待复位/重连，`0xFFFE` 逐页发送 1024 字节，`0xFFFF` 完成 |
| STM32 直连串口 | COM 模式自动选择 | 与串口蓝牙使用同一组 IAP 命令，但直接按串口缓冲发送完整约 1033 字节页帧 |

STM32 IAP 兼容约定使用 `0x10` 扩展帧：`byte count=0`，`quantity=1024` 表示原始页长度，不能写成单字节无法表达的 `0x400`。BLE 串口蓝牙按 20 字节分片、带响应写入并按 19200 波特率动态排空；直连 COM 不受 BLE 20 字节限制。每页等待并校验 Modbus ACK，旧例程没有页序号和幂等保证，因此 ACK 超时时不盲目重传。

固件文件还要经过目标架构、长度、向量表和 APP 地址检查。STM32 APP 当前按 `0x08001C00` 运行区解析，最后一页用 `0xFF` 补齐；Telink 文件和 STM32 文件不能混用。升级后会等待重启，重新连接并读取身份/实时数据验证。

当前 STM32 例程已经有边界检查、CRC、页 ACK 和升级后恢复验证，但 IAP 本身尚没有整包签名和完整镜像认证，不能单独作为量产防篡改安全保证。

## 4. 通信协议基线

### 4.1 Modbus RTU 公共规则

- 从站地址：`0x01`；
- 功能码：标准读取 `0x03`、单寄存器写 `0x06`、多寄存器写 `0x10`；
- CRC16：初值 `0xFFFF`，多项式 `0xA001`，低字节在前；
- 响应可以被 BLE 或串口分成任意长度片段，`BmsClient` 按期望长度拼帧后再做 CRC 和字段校验；
- 异常帧必须同时检查功能码和异常码，不能用“收到任意字节”判定成功。

核心常量集中在 `BmsTool.Windows/ModbusRtu.cs`：

| 地址/常量 | 含义 |
|---:|---|
| `0x0000` | MAC，可选 |
| `0x0100` | 蓝牙名，可选 |
| `0x1005` | SOC 写入 |
| `0x1007` | 完整版日志删除 |
| `0x1102` | 休眠命令 |
| `0x2100..0x2140` | 65 项 MCU 软件保护参数 |
| `0x2319` | 循环次数写入 |
| `0x2400..0x2417` | SH367309 AFE 参数，专用 |
| `0x2500` | SH3673520 型号/版本识别起址 |
| `0x2700..` | Flash 寿命测试，专用固件 |
| `0xC002` | 序列号/生产信息 |
| `0xC008` | 事件日志 |
| `0xC012` | 硬件版本 |
| `0xC022` | 软件版本 |
| `0xD000` | Legacy 实时数据窗口 |
| `0xD115` | 系统状态 |
| `0xD120` | 新实时窗口，首字 magic `0x4253` |

### 4.2 实时数据兼容探测

连接后 `BmsClient.ProbeAsync()` 最多尝试三次：

1. 读取 `0xD120` 两字，首字为 `0x4253` 时确认新实时协议；
2. 若新窗口不可用，读取 `0xD000` Legacy 头部；
3. Legacy 头部为空时，再读取 `0xC002` 生产信息窗口确认设备存在；
4. 失败前执行完整 BLE/GATT 重连，而不是在同一失效句柄上连续发包。

实时快照按当前实现读取：

- `0xD000` 起 63 字；
- `0xD115` 起 2 字系统状态；
- `0xD120` 起 11 字，若 magic 正确则用其中的总压、电流、SOC、温度和单体极值覆盖 Legacy 对应字段；
- Legacy 前 32 字始终按电压槽位处理，`61001` 为缺串哨兵值；
- 电压单位为 mV，总压为 0.01 V，电流为 0.1 A，温度按 `raw / 10 - 40` ℃，容量为 0.01 Ah。

### 4.3 Factory Session

Factory Session 使用独立功能码 `0x41`，不占用普通客户寄存器。它是 RAM-only 的临时测量输入层：不改 AFE/ADC raw、不改正式保护参数、不写 Flash。

命令：

| 命令 | 作用 |
|---:|---|
| `0x01` | OPEN；magic `0x46414354`，返回 token、超时、协议版本、串数 |
| `0x02` | HEARTBEAT；刷新会话并返回剩余时间 |
| `0x03` | INJECT；注入 cell/pack/current/temp/MOS-temp/SOC |
| `0x04` | CLEAR；清除全部临时注入 |
| `0x05` | CLOSE；关闭会话 |
| `0x06` | STATUS；返回有效输入、L1/L2/L3 和 MOS 状态 |

当前超时约 8 秒。断链、心跳超时、复位、CLEAR、CLOSE 都应清除 RAM 注入。输入类型为：cell mV、pack cV、有符号 0.1 A、电池温度 raw、MOS 温度 raw、SOC 百分比。cell 注入会重算有效最大/最小/压差和相关总压派生值；pack 显式注入可以覆盖总压。

## 5. 出厂测试功能（完整版）

`FactoryTestEngine` 支持完整测试和单项测试。两者都必须先 OPEN、读取正式保护参数、检查基线，再进行注入和恢复，最后在 `finally` 中 CLEAR、CLOSE。

当前覆盖 13 项：

| 测试项 | 注入 | 保护位 |
|---|---|---|
| 单体过压/欠压 | cell | bit0 / bit1 |
| 总压过压/欠压 | pack | bit2 / bit3 |
| 充电/放电过流 | 正/负 current | bit4 / bit5 |
| 充电高温、低温 | temp | bit6 / bit8 |
| 放电高温、低温 | temp | bit7 / bit9 |
| MOS 高温 | MOS-temp | bit13 |
| 单体压差过大 | 两串 cell | bit10 |
| SOC 过低 | SOC | bit12 |

每个项目按 L1/L2/L3 依次执行：

```text
CLEAR → 等待正常 → 按正式阈值生成边界外输入
      → HEARTBEAT + STATUS 等待滤波/触发
      → 记录 L1/L2/L3/MOS
      → CLEAR → 等待恢复 → 记录恢复结果
```

正式参数为 0 的级别按固件语义跳过；高阈值使用 `threshold + 1`，低阈值使用 `threshold - 1`；过流恢复等待覆盖固件约 30 秒策略。测试报告默认保存到用户文档 `BmsFactoryReports`，包含步骤、原始故障字、MOS 状态和 `CleanupCompleted`。

该测试验证的是 MCU 软件保护链路，不替代 AFE 芯片硬件保护、真实温箱、真实负载、MOS 驱动反馈或整机安全认证。

## 6. Flash 寿命测试（完整版）

完整版的“Flash寿命测试”只对启用 `FLASH_ENDURANCE_TEST_ENABLE=1` 的专用固件开放。它会真实写入 SOC journal，统计提交、保存、跳过、失败、回读不一致、编程失败和物理页擦除次数，并在开始前把原 SOC 快照绑定序列号备份到用户文档 `BmsFlashTests`。

支持 SOC 变化、重复值、小幅往返和强制保存等压力模式；停止或异常后尝试恢复原快照。恢复失败不能当作成功，必须保留备份人工处理。该功能会消耗真实 Flash 寿命，不能在普通客户板或不稳定供电环境运行。细节以 [Flash 寿命测试说明](../bms-tool-windows/docs/flash_endurance.md) 为准。

## 7. 日志、报告和发布

### 7.1 诊断日志

`SessionLogger` 记录启动、扫描、连接阶段、BLE/GATT、串口、Modbus TX/RX、CRC/异常、轮询、参数、OTA、Factory 和导出操作。连接失败尤其应保留完整日志，因为页面弹窗只显示摘要。

### 7.2 报告位置

| 内容 | 默认位置 |
|---|---|
| Factory JSON | `%USERPROFILE%\\Documents\\BmsFactoryReports\\` |
| Flash 测试 | `%USERPROFILE%\\Documents\\BmsFlashTests\\` |
| 长期监控 | 用户在保存对话框选择 `.xlsx` 路径 |
| 构建临时中间文件 | `%LOCALAPPDATA%\\CodexTemp\\bms-tool-windows\\` |

### 7.3 双版本构建

统一入口是 `bms-tool-windows/build-release.ps1`，同时发布客户版和完整版到各自 `publish` 子目录，使用 self-contained、single-file、win-x64，并打印 SHA-256 和源码 commit。

需要注意：两个 `.csproj` 当前声明 `net8.0-windows10.0.19041.0`，而 `build-release.ps1` 默认参数仍是 `net7.0-windows10.0.19041.0`，脚本通过 MSBuild 属性覆盖目标框架。这个行为虽然可用于既有发布流程，但会造成维护者误解，后续应统一默认目标框架并在 CI 固定检查。

## 8. 当前问题与风险清单

### P0：量产安全风险

1. STM32 现有 IAP 仍缺少整包 SHA/签名验证、版本回滚策略和设备身份绑定；文件边界和逐页 ACK 不能证明镜像未被篡改。
2. 客户版密码 `hs456` 是硬编码 UI 门槛，无法防止逆向或直接构造 Modbus 帧；固件侧必须有真正的写权限和 OTA 安全策略。
3. AFE 硬件保护写入是高风险持久化操作，目前依赖页面确认、范围校验和回读，尚未形成基于设备身份、操作者和审计记录的授权链。

### P1：实机验证缺口

1. 当前仓库中的协议/编解码/模拟测试和构建不能替代真实 BLE、直连 COM、串口蓝牙、STM32 APP/IAP 的全流程验证。
2. 3520 参数实际板卡读取、写入、异步应用和异常恢复仍需按不同固件版本实测。
3. 100/500 条日志尚未覆盖所有实际日志容量固件和跨页产生新日志的场景；当前没有设备端冻结快照。
4. 休眠后的唤醒、重连、日志删除、Flash 寿命测试的断电恢复都需要硬件测试记录。

### P1：协议和架构问题

1. 上位机仍有 Legacy 窗口、可选实时窗口、可选 MAC/蓝牙名、SH367309 地址和 SH3673520 地址等历史兼容分支，缺少统一 capability/descriptor 协议。
2. AFE 硬件参数仍是具体芯片的静态表，公共页面还没有真正的 AFE 插件/描述器接口；更换 AFE 仍可能修改公共代码。
3. 串口波特率可编辑但没有自动探测、设备身份绑定和配置持久化；输入错误波特率时只能靠诊断日志定位。
4. 两版源代码仍存在部分文件复制与链接并存的维护模式，若未来新功能没有放入 Shared，客户版和完整版容易出现行为漂移。
5. Factory Session 的注入只验证软件保护，不验证 AFE 硬件保护，这是设计边界，但界面和报告需要持续强调，避免把软件 PASS 当成整机 PASS。

### P2：体验、性能和可观测性问题

1. BLE、串口和 IAP 的等待、分片、超时策略散落在不同实现中，出现问题时需要阅读长诊断日志，缺少结构化阶段状态和错误码。
2. OTA 当前按 ACK 串行推进，安全性较好但速度受串口 19200、BLE 20 字节分片和旧 IAP 缺少流水窗口限制；不能仅通过去掉 ACK 等待提速。
3. 长期监控只保存在内存，程序异常退出会丢失未导出数据；导出过程也没有增量写入或自动恢复。
4. 事件日志页没有筛选、导出、绝对时间恢复和一致性快照；未知事件只能显示编号。
5. 尚无正式 CI 把两版编译、协议测试、发布产物哈希和工作树污染检查固化。

## 9. 优化方向与优先级

### 第一阶段：先补安全和可验证性

- 为 STM32 IAP 增加整包长度、整包 CRC/SHA-256、签名、目标设备身份、最低版本和回滚保护；每页增加明确序号/偏移，支持只在协议保证幂等时重传；
- OTA 开始前增加电源、目标架构、版本、地址范围、镜像摘要和设备能力预检；结束后验证摘要、版本和可读取状态；
- 把软件保护、AFE 参数、OTA、Flash 测试统一纳入设备权限模型，UI 密码只作为界面便利；
- 报告增加固件 commit、上位机 commit、协议版本、AFE 型号、传输方式、串口参数、镜像 SHA-256、设备序列号和清理结果；
- 建立真实硬件矩阵：Telink BLE、STM32+串口蓝牙、直连 COM、100/500 日志、旧/新 AFE、断链/复位/断电。

### 第二阶段：完成 AFE 可插拔模板

建议新增公共能力模型：

```text
DeviceCapability
  ├─ 公共实时数据版本、串数、缺省值语义
  ├─ Factory Session 版本和输入能力
  ├─ OTA 目标和最大传输能力
  └─ AfeCapability
       ├─ afe_id / 型号 / 版本
       ├─ 支持的硬件保护、均衡、温度、通道数
       ├─ 参数 descriptor（逻辑 ID、单位、范围、步进、枚举）
       └─ 读写/持久化/异步应用状态
```

固件公共层只接收统一测量结构和 AFE 状态，不直接访问 `ram_reg_309` 或具体芯片寄存器。Windows 公共页面只消费统一 descriptor，SH367309、SH3673520 和未来 AFE 各自提供 codec/provider。新 AFE 不支持某项时返回明确 `unsupported`，不能返回 0 伪装成功。

### 第三阶段：提升上位机工程质量

- 以 `BmsClient` 为核心增加能力缓存和统一状态机，减少页面直接操作传输层；
- 把诊断日志改为结构化事件（时间、阶段、方向、帧摘要、异常类型、重试原因），同时保留可读文本；
- 加入虚拟传输层和故障注入测试：分片、延迟、CRC 错、短帧、重复帧、断链、设备复位；
- 长期监控采用 SQLite/CSV 增量落盘，支持暂停后恢复和大数据量导出；
- 事件日志增加导出、过滤、容量/协议版本显示；设备端若允许，增加冻结快照或读取游标；
- CI 固定 net8 目标框架、同时构建两版、运行 PowerShell 回归脚本、检查发布文件和 SHA-256，并确认 `bin/obj/publish` 不进入源码提交。

## 10. 建议开发路线图

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| R0 当前基线 | 保持双版本、BLE/串口、公共监控、Factory、OTA 可维护 | 两版 Release/self-contained 构建成功；协议测试通过；未验证项有清单 |
| R1 安全 OTA | 安全镜像和可靠传输 | 非目标镜像拒绝；签名/摘要/版本/设备绑定校验；断点/重传有明确语义；升级后可恢复 |
| R2 能力协议 | 设备能力和 AFE descriptor | 新 AFE 只修改 driver/adapter/descriptor；公共上位机逻辑不改；不支持功能不可写 |
| R3 自动化测试台 | 真机夹具、自动采集和追溯 | 每台设备生成可审计报告；Factory、AFE 硬件、OTA、日志和恢复状态分层记录 |
| R4 产品化体验 | 稳定、可诊断、可扩展 | 长期数据增量保存；结构化日志；CI 发布；客户版与完整版边界自动检查 |

## 11. 更换 AFE 时的最小修改原则

### 应该修改的部分

- 新 AFE 驱动、初始化、采样和通信错误处理；
- 固件 AFE adapter/capability；
- AFE 参数 descriptor、物理单位 codec、异步应用状态；
- AFE 专属硬件保护和诊断页面；
- 对应实机测试、协议版本和文档。

### 原则上不应修改的部分

- BLE/串口传输适配器；
- Modbus CRC、公共帧解析和公共异常处理；
- `BatterySnapshot` 公共字段和 32 槽位/`61001` 语义；
- MCU 软件保护参数和 L1/L2/L3 逻辑；
- Factory Session、自动/单项测试编排、报告 finally 清理；
- 日志、长期监控和客户版基础页面；
- Telink OTA 和已安全化后的 STM32 OTA 公共流程。

若新 AFE 无法提供当前公共测量单位或保护输入，应增加协议版本/能力降级，不要在公共页面里加入芯片型号判断。

## 12. 维护者接手清单

接手新功能时，建议按以下顺序检查：

1. 先确认修改属于固件、公共上位机、客户版、完整版还是 AFE 专属层；
2. 读取 `bms-tool-windows/README.md`、本文以及对应的 `docs/factory_test_protocol.md`、`docs/windows_serial_connection.md`、`docs/3520_parameters.md`；
3. 任何协议地址和字段都必须回到 BMS 实际源码或现有协议实现核对，不能凭名称猜测；
4. 公共功能优先修改 `BmsTool.Windows` 的核心文件或 `Shared`，完整版通过项目链接复用；
5. 修改写操作时必须有 ACK、CRC、地址/数量/值回读或明确的设备端完成状态，禁止盲目重发；
6. 功能结束后分别构建客户版和完整版，运行对应回归脚本；
7. 记录真实硬件是否验证、设备型号、固件版本、连接方式和未解决问题；
8. 提交时只提交源码和正式文档，不提交 `bin/`、`obj/`、发布缓存或临时文件。
