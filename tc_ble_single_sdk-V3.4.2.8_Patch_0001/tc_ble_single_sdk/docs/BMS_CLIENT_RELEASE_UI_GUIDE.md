# BMS Client 发布、费用与 UI 总览

> 面向开发人员、测试人员和 AI/Codex。用于回答：各端如何测试/发布、微信小程序是否必须上架、可能有哪些费用、各端 OTA 到什么阶段、各端 UI 当前长什么样。

## 1. 状态术语

本文严格区分：

- **已实现**：代码路径已经存在，并通过对应静态/协议测试。
- **可构建**：目标平台编译/打包链路通过。
- **已实机验证**：真实 BMS + 目标手机/PC 完成 BLE/OTA 闭环。
- **已发布**：已经通过平台审核并向普通用户正式发布。

AI MUST NOT 把“已实现”描述成“已实机验证”或“已发布”。

## 2. 微信小程序：测试、发布与费用

### 2.1 开发/测试不需要正式上架

开发阶段可使用：

- 微信开发者工具；
- 真机预览/真机调试；
- 开发版；
- 体验版。

BLE 必须以手机真机为最终测试环境。开发版/体验版适合内部人员和指定体验人员，不要求先发布正式版。

### 2.2 面向任意普通微信用户时需要正式发布

如果目标是让任意客户通过微信搜索、小程序码或分享入口直接使用，应走：

```text
注册小程序
  -> 配置主体/服务类目
  -> 上传代码
  -> 提交微信审核
  -> 审核通过
  -> 发布正式版
```

未正式发布时，不应把开发版/体验版当作面向全部客户的交付方式。

### 2.3 费用原则

- 微信小程序代码“提交审核/发布一个版本”本身不是按版本收取上架费。
- 开发、预览、体验版测试本身不需要购买服务器。
- 当前 BMS 小程序的 BLE 状态读取与 OTA 都是手机和 BMS 本地 BLE 直连，V1 不依赖云服务器，因此仅使用当前功能时没有必须的云服务器费用。
- 如果后续增加账号、云端设备管理、远程数据、日志云同步、固件云分发等能力，才会产生相应后端/存储/流量成本。
- 微信认证可能产生审核认证费用，具体金额和周期以微信公众平台后台当时生成的订单为准。企业主体常见认证费用预算可按约人民币 300 元/认证周期预留，但禁止在产品文档中把该金额写成永久固定规则。
- 如果小程序本身不设计收费功能，最终用户使用 BMS 小程序不需要向我们支付“小程序使用费”。

### 2.4 本 BMS 项目的主体建议

面向客户正式发布时，优先使用公司/企业等**非个人主体**，并按实际功能选择合适服务类目。对于硬件设备管理场景，应优先评估“工具 > 设备管理”等类目和微信认证要求。

原因：

- 本项目不是普通内容展示，而是连接和控制真实 BMS；
- 包含参数写入和 OTA；
- 后续很可能增加设备身份、售后、权限和固件管理；
- 企业主体更适合正式产品交付和审核。

开发阶段不需要因为该建议而阻塞 BLE/OTA 真机测试。

## 3. 当前各端 OTA 状态

| 端 | OTA 代码 | UI | 自动测试 | 仍需完成 |
|---|---|---|---|---|
| Qt Windows/macOS/Linux | 已实现 | 独立 `BMSAssistantOTA` 工具 | Python OTA vectors | 目标 OS 打包 + BMS 真机升级 |
| Android | 已实现 | 独立 `BMS OTA` Activity/Launcher | Gradle + OTA codec tests | Android 手机 + BMS 真机升级 |
| iPhone/iPad | 已实现 | App 第四个 `OTA` Tab | Swift parse + shared vectors | 正式 Xcode iOS target、签名、真机升级 |
| macOS Swift | 普通 BLE 已实现 | 桌面工程 UI | Swift source checks | OTA 当前优先使用 Qt 工具 |
| 微信小程序 | 已实现 | 独立 OTA 页面 | TypeScript type-check + OTA smoke | 微信真机 BLE OTA |

统一 OTA 真源：

- `BMS_OTA_通信规范_V1.0.md`
- `ota_test_vectors.json`

所有端 MUST 复用同一 Legacy OTA wire protocol，不允许各自发明包格式。

## 4. 当前各端 UI

### 4.1 Qt 上位机（Windows/macOS/Linux）

定位：工程调试主线，信息密度最高。

主窗口：

```text
┌──────────── 左侧设备区 ────────────┬────────────── 右侧内容区 ──────────────┐
│ 扫描模式 / 搜索 / BMS 过滤          │ [电池状态] [调试工作台]              │
│ 扫描 / 连接 / 断开                   │                                      │
│ BLE 状态 / Link 状态 Badge           │ 电池状态：                            │
│ 设备列表 / RSSI / UUID / ID          │ 总压、电流、SOC、温度、单体、SOH…    │
│ 当前状态信息                         │ SystemStatus / 容量 / 快照 / 导出     │
│                                      │                                      │
│                                      │ 调试工作台：                          │
│                                      │ 身份/保护/日志/寄存器/Raw/BT Name     │
│                                      │ TX/RX 报文日志                        │
└──────────────────────────────────────┴──────────────────────────────────────┘
```

风格：桌面工程工具，浅色、卡片、状态 Badge、指标卡和表格。

OTA 当前是独立工具窗口 `BMSAssistantOTA`，而不是和普通 Modbus 会话混在同一 pending queue 中。

### 4.2 Android App

定位：移动工程版。

顶部：

- `BMS Assistant Android`；
- 当前连接状态；
- Echo 快捷按钮；
- 导出电池 JSON。

设备区：

- 扫描/停止/连接/断开；
- 扫描模式；
- 名称/地址过滤；
- “只显示疑似 BMS”；
- 设备列表、RSSI、广播 UUID。

主内容目前两页：

```text
[电池状态] [调试工作台]
```

电池状态页：

- 总压、电流、SOC；
- Max/Min/MOS 温度；
- Cell Max/Min/Delta；
- SOH、Cycle Count、容量；
- 单体电压卡片；
- SystemStatus 状态 Chip；
- 1s/2s/5s 自动刷新；
- JSON 导出。

调试工作台：

- 设备身份；
- 保护参数/事件日志；
- 手动寄存器读写；
- Echo；
- Raw Modbus；
- 写 SOC；
- 写蓝牙名；
- CSV 日志导出。

OTA 当前作为独立 `BMS OTA` Activity/Launcher，避免和普通 App 自动刷新抢 BLE 会话。

### 4.3 iPhone/iPad App

定位：用户/工程移动端共用基础。

底部 Tab：

```text
[设备] [电池] [工程] [OTA]
```

设备：扫描、过滤、设备列表、连接/断开。

电池：2 列指标卡 + 单体电压 + SystemStatus + 设备信息。

工程：Echo、SOC、蓝牙名、保护预览、事件日志、SystemStatus 等工程操作。

OTA：文件选择、固件校验、OTA 连接、进度、结果和错误提示。

当前 iOS 源码已经具备移动 UI，但正式客户交付前仍需建立/完善 Xcode iOS App target、Signing 与真机安装链路。

### 4.4 macOS Swift App

定位：Apple 原生桌面工程工具。

当前继续保留大屏桌面布局，复用 `AppModel + CoreBluetooth + ModbusCodec`。普通 BLE 功能和工程操作已存在；桌面 OTA 首轮统一以 Qt OTA 工具作为主验证入口，避免同时维护两个桌面 OTA 工具链。

### 4.5 微信小程序

定位：安装成本最低的轻量客户端。

主页面：

```text
BMS Assistant
├─ 设备
│  ├─ 扫描 / 连接 / 断开
│  └─ BT_* 设备列表
├─ 电池状态
│  ├─ 总压 / 电流 / SOC / SOH
│  ├─ 温度 / Cell Max / Delta
│  ├─ 单体电压
│  └─ 刷新 / Echo
├─ 设备信息
│  └─ MAC / SN / HW / SW
├─ 工程写操作
│  └─ SOC / 蓝牙名
├─ 固件 OTA 入口
└─ 通信日志
```

OTA 页面：

- 扫描 BMS；
- 选择设备并连接 OTA Characteristic；
- 从微信会话选择 `firmware.bin`；
- KNLT/size 校验；
- 进度条；
- OTA_RESULT；
- OTA 日志。

小程序的 firmware 二进制保存在逻辑层，不写入 `setData()`，避免把大块二进制同步到 WXML 视图层。

## 5. UI 产品化方向

当前 UI 首先服务“协议和硬件联调”，不是最终客户视觉稿。下一轮产品化时应统一：

- 用户模式：只显示电池状态、单体、告警、设备信息、OTA；
- 工程模式：开放保护参数、寄存器、日志、Raw、校准等；
- 危险写操作必须二次确认并受权限控制；
- OTA 在正式客户版中必须增加固件可信校验/权限策略；
- 四端命名、单位、状态图标、报警颜色和参数分组保持一致。

## 6. 发布前最小验收

### 微信小程序

- 开发者工具 type-check；
- Android 微信真机；
- iPhone 微信真机；
- 普通 BLE 读取；
- 分片响应；
- 断连恢复；
- OTA 成功；
- OTA 错误固件；
- 提审前检查主体、类目、隐私与危险操作说明。

### 原生 App / Qt

- 构建/打包；
- BLE 扫描连接；
- 普通业务全流程；
- OTA；
- 重启后版本回读；
- 断电/断连/超时/错误固件等异常场景。
