# mac BLE 扫描问题与电池状态页说明

## 1. 文档目的

这份文档专门说明两件事：

1. 为什么当前 `Mac` 上位机一开始“看不到”或“看错”当前项目的 `BT_*` BMS BLE 设备。
2. 为什么需要在固件里新增一页稳定的实时数据寄存器，并在上位机里单独做一页“电池状态”。

文档结论基于 2026-04-06 在当前工程目录下做的系统级扫描验证、固件广播代码核对、以及上位机代码行为核对。

## 2. 最终结论

问题不在系统蓝牙硬件，不在 `Mac` 无法扫描 BLE，也不在当前固件没有广播。

真实问题有两层：

1. `CoreBluetooth` 对同一块板子同时给出了两个名字：
   - `localName = BT_DEFAULT`
   - `peripheralName = tSample`
2. 旧版上位机在列表展示和过滤时没有把这两个名字分开处理，导致用户按 `BT` 认设备时，容易把板子误看成别的设备，或者在噪声很多时直接错过。

另外，当前固件把蓝牙名放在 `scan response`，不在主广告包里。这会进一步放大 `Mac` 侧名字识别的不稳定性。

## 3. 现象与证据

### 3.1 系统级独立扫描已经确认板子存在

在 2026-04-06 通过独立 `CoreBluetooth` 探针扫描到如下目标记录：

- `localName`: `BT_DEFAULT`
- `peripheralName`: `tSample`
- `advertisedServices`: `1812`, `180F`
- `isConnectable`: `true`
- `RSSI`: `-76`

这说明：

- 板子确实在广播
- `Mac` 确实能收到这块板子的 BLE 广播
- 板子不是“扫不到”

### 3.2 固件广播结构本身就容易让上位机误判

当前固件广播结构是：

- 主广告包 `ADV` 只带：
  - Flags
  - Appearance
  - 16-bit UUID 列表 `0x1812`, `0x180F`
- 蓝牙名 `BT_*` 放在 `scan response`

这意味着：

- 某些扫描时刻，`Mac` 可能先拿到主广告包
- 这时用户可见的主名字不一定立刻是 `BT_*`
- 如果上位机只认一个名字来源，或者默认只用缓存的 `peripheral.name`，就容易误判

### 3.3 当前工程没有开启安全配对定向广播

当前工程 `BLE_APP_SECURITY_ENABLE = 0`，因此这里不是“定向广播只给某个已配对设备”的问题。

也就是说，本次现象不能归因于：

- 只对 iPhone 定向广播
- Mac 没有 bond 记录
- SMP 配对策略不同

## 4. 根因拆解

### 4.1 根因一：`localName` 与 `peripheralName` 混用

对当前这块板子，系统独立扫描已经证明：

- 广播名是 `BT_DEFAULT`
- 同时 `CoreBluetooth` 还返回了一个 `peripheralName = tSample`

如果上位机：

- 优先使用 `peripheral.name`
- 或者过滤逻辑只看一个名字字段
- 或者列表里不把第二个名字展示出来

那么用户就会认为“板子不在列表里”。

### 4.2 根因二：名字在 `scan response`，不在主广告包

当前固件的 `BT_*` 名字不是在主广告里，而是在 `scan response` 里。

这会导致两个直接后果：

1. 列表里最早出现时，名字可能还没补全。
2. 如果扫描结果很多，用户只靠名字肉眼查找，容易漏掉目标板。

### 4.3 根因三：旧版上位机缺少“工程定位信息”

旧版上位机虽然能扫描到很多 BLE 设备，但缺少三类关键辅助信息：

1. 广播 UUID
2. `localName / peripheralName` 双名字展示
3. “当前固件扫描模式”

所以用户在噪声环境下难以把板子从大量 BLE 设备里快速筛出来。

## 5. 已完成的修复

### 5.1 扫描与设备识别修复

上位机已做以下修复：

- 优先显示 `localName`
- 如果 `peripheralName` 与 `localName` 不同，则显示为“别名”
- 搜索过滤同时匹配：
  - 主显示名
  - 别名
  - 广播 UUID
- 新增扫描模式：
  - `当前固件`
  - `全部设备`
- 列表中直接显示：
  - RSSI
  - 广播 UUID
  - `Connectable`

### 5.2 新增系统级探针工具

已新增独立探针脚本用于直接验证 `Mac` 是否收到板子广播：

- `vendor/ble_sample/BMSAssistant/scripts/run-ble-probe.sh`

这个工具不依赖上位机 UI，可以直接输出附近 BLE 广播的 JSON 结果，用于排查“系统没收到广播”还是“UI 逻辑误判”。

## 6. 为什么还要新增“电池状态页”

原因很直接：

当前固件对工程调试已经暴露了一批寄存器，但它们更像“内部数组平铺”，不是稳定的上位机业务模型。

例如：

- `0xD000`~`0xD01F` 是 `u16VCell[32]`
- 数组里混有：
  - 单体电压
  - 电池温度 ADC
  - MOS 温度 ADC
  - 总压 ADC

这对寄存器浏览器很有用，但不适合直接做首页状态页。

用户想看的首页核心信息其实是：

- 电压
- 电流
- 温度
- SOC

所以更合理的做法不是让 UI 去猜内部数组，而是让固件明确给一页“稳定业务寄存器”。

## 7. 新增稳定实时数据寄存器窗口

为配合电池状态页，当前实现新增一页稳定实时寄存器窗口：

- 地址范围：`0xD120` ~ `0xD12A`
- 总计：`11` 个寄存器

### 7.1 寄存器表

| 地址 | 含义 | 单位/编码 | 说明 |
| --- | --- | --- | --- |
| `0xD120` | Magic | `0x4253` | 用于识别窗口是否存在 |
| `0xD121` | Version | `0x0001` | 当前窗口版本 |
| `0xD122` | Pack Voltage | `V * 100` | 例如 `4200 -> 42.00V` |
| `0xD123` | Pack Current | `signed A * 10` | `Int16` 二补码；充电为正，放电为负 |
| `0xD124` | SOC | `%` | `0~100` |
| `0xD125` | Max Temp | `(+40°C) * 10` | 需要上位机换算 |
| `0xD126` | Min Temp | `(+40°C) * 10` | 需要上位机换算 |
| `0xD127` | MOS Temp | `(+40°C) * 10` | 需要上位机换算 |
| `0xD128` | Max Cell Voltage | `mV` | 最高单体 |
| `0xD129` | Min Cell Voltage | `mV` | 最低单体 |
| `0xD12A` | Cell Delta | `mV` | 单体压差 |

### 7.2 上位机换算规则

- `Pack Voltage`: `raw / 100.0`
- `Pack Current`: `Int16(bitPattern: raw) / 10.0`
- `SOC`: 直接显示 `%`
- `Temp`: `raw / 10.0 - 40.0`
- `Cell Voltage / Delta`: 直接显示 `mV`

## 8. 上位机页面规划调整

当前上位机已改成两页结构：

1. `电池状态`
   - 只展示稳定业务量
   - 不放原始调试控件
   - 主展示：
     - `Pack Voltage`
     - `Pack Current`
     - `SOC`
     - `Max Temp`
     - `Min Temp`
     - `MOS Temp`
     - `Cell Max`
     - `Cell Min`
     - `Cell Delta`
2. `调试工作台`
   - 保留原来的调试入口
   - 包括：
     - 原始寄存器读写
     - Echo
     - 事件日志
     - 保护参数
     - 蓝牙名写入
     - 原始帧发送

这样做的好处是：

- 首页状态页不会再被调试控件污染
- 工程调试和日常查看状态分离
- 协议层也形成了稳定边界

## 9. UI 颜色调整说明

这次 UI 还同步做了两点调整：

1. 背景整体从深色改为浅色工程风
2. 卡片、日志块、原始帧区域全部提亮

这样可以解决之前“页面偏暗、数据区不够清晰”的问题。

## 10. 使用注意事项

### 10.1 如果你想看到新的电池状态页数据

需要保证板子运行的是包含本次实时寄存器窗口的最新固件。

如果板子还是旧固件：

- 上位机仍然能连接
- 调试页仍然能用
- 电池状态页会自动退回旧寄存器兼容模式
- 兼容模式下可以显示：
  - `Cell 1 ~ Cell 10` 单串电压
  - `Pack Voltage`
  - `Pack Current`
  - `SOC`
  - `Max/Min/MOS Temp`
  - `SystemStatus` 状态字
  - 电池温度 / MOS 温度 ADC 原始值
- 这里依赖的是当前工程 `stCell_Info` 从 `0xD000` 起连续平铺到 `0xD03E` 的事实，不是独立稳定协议页

### 10.2 如果你在 Mac 上再次怀疑“扫不到板子”

优先做下面两步：

1. 先用系统探针 `run-ble-probe.sh` 看系统是否收到 `BT_*`
2. 再看上位机列表里是否出现：
   - 主名：`BT_*`
   - 别名：例如 `tSample`
   - UUID：`180F`, `1812`

## 11. 结论

这次问题的本质不是 BLE 链路本身故障，而是：

- 固件广播名放在 `scan response`
- `CoreBluetooth` 对同一设备存在双名字来源
- 上位机在工程噪声环境下缺少足够的定位信息

对应的长期正确修复路径是：

1. 让扫描页显示更完整的广播上下文
2. 用稳定业务寄存器支撑状态首页
3. 把状态页和调试页分离

这三件事现在都已经在当前工程里落地。
