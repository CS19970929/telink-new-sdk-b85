# flash_kv32 设计说明

## 1. 目标

本次重构目标不是继续补丁式修 `soc_kv_store`，而是抽出一个可复用的 `flash_kv32` 通用持久化层，满足下面几个要求：

- 支持更多 `key -> u32` 数据项，后续扩展只需要新增 key。
- 支持可配置扇区大小、扇区数量、分区地址，避免把格式写死在业务代码里。
- 支持冷热分区，高频数据和低频数据可以分开建库，减少相互拖累。
- 支持掉电恢复，不能因为半写入、切换中断、尾部脏数据而恢复出错误值。
- 支持磨损均衡，不能长期只在两个固定扇区之间来回擦写。
- 易移植到其他 MCU，核心逻辑不直接依赖 Telink Flash 驱动细节。

## 2. 设计范围

本层只解决“小量参数持久化”问题，明确约束如下：

- 值类型固定为 `u32`。
- key 固定为编译期定义，不做运行时动态创建。
- 不做文件系统，不做变长对象，不做大块数据存储。
- 不依赖动态内存，所有缓存由调用方静态提供。

这个约束是刻意收窄后的结果。对当前项目来说，`SOC / DSG / cycle / 运行计数 / 校准参数 / 配置参数` 都属于这类场景，固定宽度反而最简单、最稳。

## 3. 总体结构

### 3.1 核心分层

拆成三层：

1. `flash_kv32`
   - 只处理通用 Flash 日志、扫描、压缩、恢复。
   - 不知道业务字段含义。

2. `flash port`
   - 只暴露读、写、擦除接口。
   - 适配 Telink 或其他 MCU 的底层 Flash 驱动。

3. 业务封装
   - 例如 `soc_kv_store`。
   - 只负责把业务字段映射成 key。

### 3.2 冷热分区

冷热分区不再在一个扇区池里混写，而是拆成多个独立实例：

- 热区：SOC、循环次数、运行计数等高频更新数据。
- 冷区：配置参数、校准参数、出厂参数等低频更新数据。

每个分区都是一个独立的 `flash_kv32` 实例，各自有：

- 自己的扇区地址列表
- 自己的扇区数量
- 自己的 RAM 缓存
- 自己的擦写节奏

这样做的好处：

- 热区频繁 GC 不会拖着冷区一起搬迁。
- 冷区稳定参数不会被高频日志反复重写。
- 后续如果新增第三类数据，也可以继续独立分区。

## 4. Flash 格式

### 4.1 统一采用手工序列化

Flash 上的数据格式不直接写 C 结构体，而是统一使用手工小端序列化，原因如下：

- 避免不同编译器的对齐、打包、字节序差异。
- 降低迁移到其他 MCU 时的格式风险。
- 格式演进可以更清晰地做版本控制。

### 4.2 扇区头

每个扇区头固定长度，包含：

- `magic`
- `version`
- `header_size`
- `generation`
- `record_area_offset`
- `header_crc32`
- `prepare_mark`
- `active_mark`

说明：

- `prepare_mark` 表示该扇区已被初始化，准备接收数据。
- `active_mark` 表示该扇区已经完成提交，可以作为有效扇区参与恢复。
- `generation` 用来判定多个有效扇区的新旧顺序，不能再靠写偏移猜测。

### 4.3 事务记录

分区内部采用 append-only 日志，每条事务记录包含：

- 事务头
  - `magic`
  - `version`
  - `item_count`
  - `seq`
  - `payload_len`
  - `total_len`
  - `crc32`
- `item_count` 个 item
  - `key`
  - `value`
- 事务尾
  - `commit_magic`

说明：

- 一次事务可以写一个或多个 key。
- `soc/dsg/cycle` 可以在一条事务里一起提交，避免中间状态落盘。
- `commit_magic` 最后写入，用来识别半写事务。
- `crc32` 保护事务头和 payload，避免误把脏尾当成有效数据。

### 4.4 对齐和扇区大小

每条事务的总长度会按 `write_align` 向上对齐，末尾补 `0xFF`。  
这样可以兼容不同 MCU 的最小编程粒度要求，扇区大小也通过配置传入，不在代码里写死 `4096`。

## 5. 启动恢复规则

启动扫描时按下面的顺序处理：

1. 扫描所有扇区头。
2. 找出头有效且 `active_mark` 完成的扇区。
3. 从中选 `generation` 最大的扇区作为当前活动扇区。
4. 顺序扫描事务日志，只接受：
   - 事务头合法
   - 长度合法
   - `commit_magic` 完整
   - CRC 正确
5. 一旦遇到非擦除态的非法尾部，停止扫描并标记 `tail_dirty`。

这样定义后：

- 写事务中途掉电，未提交事务会被直接忽略。
- 扇区切换中途掉电，只要新扇区未完成 `active_mark`，仍回退到旧扇区。
- 如果新扇区已完成 `active_mark` 但旧扇区尚未擦除，则用更大的 `generation` 选中新扇区。

## 6. 写入与压缩策略

### 6.1 日常写入

普通写入只追加事务，不原地修改旧数据。

如果要写入的数据和缓存值完全一致，则直接跳过，不产生无效写放大。

### 6.2 压缩触发条件

出现下列情况之一时触发压缩：

- 当前扇区剩余空间不足以写下下一条事务。
- 扫描后发现 `tail_dirty`，不能继续原地追加。
- 调用方主动请求 compact。

### 6.3 压缩流程

压缩使用“下一扇区接管”的方式：

1. 选择环形下一个扇区作为目标扇区。
2. 擦除目标扇区。
3. 写入扇区头，并写 `prepare_mark`。
4. 将当前 RAM 缓存中的有效值写成一条完整快照事务。
5. 写入 `active_mark`，目标扇区正式生效。
6. 切换运行时状态到新扇区。
7. 擦除旧扇区。

这个顺序保证：

- 不会因为旧扇区先擦掉导致整库失效。
- 切换窗口掉电后仍能靠 `generation` 恢复到最新状态。

## 7. 磨损均衡与寿命

### 7.1 基本策略

磨损均衡采用“多扇区环形轮转”，而不是固定 A/B 双备份：

- 每次压缩都切到逻辑上的下一个扇区。
- 长期运行后擦写次数会在整个分区里平摊。

### 7.2 热冷分离

冷热分区是寿命策略的一部分，而不是纯粹的逻辑分类：

- 热区建议给更多扇区。
- 冷区可以扇区更少，但保留独立 GC。

举例：

- 热区 4~8 个扇区，存 SOC、循环次数、运行计数。
- 冷区 2~4 个扇区，存配置、校准、序列号相关参数。

### 7.3 写放大控制

为了控制写放大，日常事务只写变化项；只有在 compact 时才写整区快照。  
这样可以兼顾：

- 平时写入足够省
- 恢复语义明确
- compact 逻辑简单

## 8. 可移植性

核心模块只依赖一个最小 Flash 端口：

- `read(addr, buf, len)`
- `prog(addr, buf, len)`
- `erase_sector(addr, size)`

可选扩展：

- `enter_critical()`
- `exit_critical()`

移植到其他 MCU 时，原则上只需要替换这层端口，不需要改日志格式和恢复逻辑。

## 9. 对当前项目的落地方式

### 9.1 第一阶段

先完成下面这些落地：

- 引入 `flash_kv32.c/.h`
- 保持 `soc_kv_store` 对外接口不变
- 将 `soc_kv_store` 改为 `flash_kv32` 的薄封装
- 把 `cycle` 扩成 `u32`
- 让热区地址和扇区数可配置

### 9.2 第二阶段

为冷区预留同样的接入方式：

- 配置参数可直接新建一个 `flash_kv32` 实例
- 复用相同格式和相同恢复逻辑
- 不需要再复制一份新的 Flash 存储实现

## 10. 边界与约束

本次实现仍保留几个明确前提：

- 单个分区的“当前有效 key 集合”必须能在一次 compact 时装进一个扇区。
- key 数量默认较小，查找采用线性扫描，后续如果 key 明显增多再考虑索引优化。
- 默认不做跨分区事务；冷热区之间相互独立。

这些约束对当前项目是合理的，换来的是更小的代码复杂度和更明确的掉电语义。

## 11. 本次实现结论

本次会把 `soc_kv_store` 升级成：

- 底层：可配置扇区大小、扇区数量、顺序轮转的 `flash_kv32`
- 分区：支持按实例拆分热区/冷区
- 业务层：`soc_kv_store` 只保留 key 映射和默认值定义

这样后续要新增存储项时，不再需要再写一套新的 sector 扫描和恢复代码。
