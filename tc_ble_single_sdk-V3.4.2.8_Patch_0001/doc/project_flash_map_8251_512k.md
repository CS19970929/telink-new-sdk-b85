# 当前项目 Flash 分区梳理（8251 / 512K）

## 1. 结论

- 当前项目按 `8251` 系列、`512K flash` 评估，当前正式写入区之间没有地址冲突。
- 当前 OTA 设计等价于双固件槽位，第二固件槽从 `0x20000` 开始；项目代码已经显式拒绝 `512K + OTA boot=0x40000`，因此不会踩到当前用户数据区。
- 当前业务写入区实际位于 `0x40000 ~ 0x73FFF`，SDK 顶部保留区位于 `0x74000 ~ 0x7FFFF`，两者已经隔离。
- 当前主产物 `825x_ble_sample.bin` 大小为 `88500` 字节（`0x159B4`），小于默认 OTA 固件上限 `124K`（`0x1F000`），当前 OTA 仍有 `38476` 字节（`0x964C`）余量。
- 历史 `PARAM_ADDR = 0x78000` 在 `8251/512K` 场景下已经落入 SDK 顶部保留区，当前代码只保留只读兼容，不允许再恢复为写入区。

## 2. 当前项目前提

- MCU 系列：`8251`，按 `825x` 512K 保留区规则处理。
- Flash 容量：`512K`，地址范围 `0x00000 ~ 0x7FFFF`。
- `BLE_OTA_SERVER_ENABLE = 1`。
- 工程内未调用 `blc_ota_setFirmwareSizeAndBootAddress(...)`，因此沿用 SDK 默认 OTA 配置：
  - 默认 OTA 新固件起始地址：`0x20000`
  - 默认单镜像最大固件尺寸：`124K`，即 `0x1F000`
- 当前构建产物：`project/tlsr_tc32/B85/825x_ble_sample/825x_ble_sample.bin`
  - 实际尺寸：`88500` 字节，`0x159B4`

## 3. 512K 全局 Flash Map

| 区域 | 地址范围 | 大小 | 说明 |
| --- | --- | --- | --- |
| 固件槽 A（当前运行固件可用区） | `0x00000 ~ 0x1EFFF` | `124K` | 当前运行固件必须落在这里 |
| OTA 保留尾页 A | `0x1F000 ~ 0x1FFFF` | `4K` | SDK OTA 默认不作为有效固件区 |
| 固件槽 B（OTA 新固件可用区） | `0x20000 ~ 0x3EFFF` | `124K` | OTA 下载的新固件写入区 |
| OTA 保留尾页 B | `0x3F000 ~ 0x3FFFF` | `4K` | SDK OTA 默认不作为有效固件区 |
| `event_log` | `0x40000 ~ 0x47FFF` | `32K` | 8 个 sector |
| 空闲区 A | `0x48000 ~ 0x4FFFF` | `32K` | 当前未使用 |
| `btname` | `0x50000 ~ 0x50FFF` | `4K` | 1 个 sector |
| `runtime` | `0x51000 ~ 0x52FFF` | `8K` | 2 个 sector |
| `soc_kv` | `0x53000 ~ 0x5AFFF` | `32K` | 8 个 sector |
| `cold_kv` | `0x5B000 ~ 0x5EFFF` | `16K` | 4 个 sector |
| 空闲区 B | `0x5F000 ~ 0x6FFFF` | `68K` | 当前未使用 |
| 迁移兼容区 | `0x70000 ~ 0x73FFF` | `16K` | 旧 `soc_kv/cold_kv` 来源区 |
| SDK 顶部保留区 | `0x74000 ~ 0x7FFFF` | `48K` | SMP / MAC / calibration / master pairing，不允许业务占用 |

## 4. 当前正式写入区

当前项目真实在写的业务区只有 5 组：

| 模块 | 起始地址 | 结束地址 | 大小 |
| --- | --- | --- | --- |
| `event_log` | `0x40000` | `0x47FFF` | `32K` |
| `btname` | `0x50000` | `0x50FFF` | `4K` |
| `runtime` | `0x51000` | `0x52FFF` | `8K` |
| `soc_kv` | `0x53000` | `0x5AFFF` | `32K` |
| `cold_kv` | `0x5B000` | `0x5EFFF` | `16K` |

这些区域彼此不重叠，也没有碰到 OTA 固件槽和 SDK 顶部保留区。

## 5. 历史兼容区与容易误判的旧地址

### 5.1 旧 KV 迁移来源区

- `prev soc_kv`：`0x70000 ~ 0x71FFF`
- `prev cold_kv`：`0x72000 ~ 0x73FFF`

这两段现在不是正式业务写入区，只用于旧版本数据迁移。当前布局已经把它们和正式写入区隔开。

### 5.2 Legacy 别名

- `legacy btname`：`0x50000`
- `legacy runtime`：`0x51000`
- `legacy hot kv`：`0x70000`

其中：

- `legacy btname`、`legacy runtime` 在 512K 当前布局里与正式地址相同，不构成额外冲突。
- `legacy hot kv` 已经退化为迁移来源区，不再是当前正式写入区。

### 5.3 最需要特别标出来的历史地址

- `PARAM_ADDR = 0x78000`

这个地址在 `8251/512K` 场景下已经位于 SDK 顶部保留区内。当前代码仍然会在启动时做一次只读兼容读取，用来迁移极老版本参数；但当前保存路径已经切到 `cold_kv`，不能再把 `0x78000` 当作可写参数区使用。

### 5.4 历史 `event_log` 宏

- 历史宏 `FLASH_ADDR_LOG_BASE = 0x72000`

这个值已经不是当前 `event_log` 的正式地址。当前 `event_log` 实际写入地址是 `0x40000`。`0x72000` 现在属于旧布局兼容区的一部分，不能再按“现网日志区”理解。

## 6. 与 OTA 的关系

### 6.1 当前 OTA 为什么不冲突

- 当前项目默认 OTA 新固件槽从 `0x20000` 开始。
- 当前业务写入区从 `0x40000` 开始。
- 因此，当前 OTA 槽 B 与业务存储区之间天然隔开。

### 6.2 当前固件大小是否仍然安全

- 当前 `825x_ble_sample.bin = 0x159B4`
- 默认 OTA 最大镜像 = `0x1F000`
- 当前余量 = `0x1F000 - 0x159B4 = 0x964C`

所以当前版本在默认 `0x20000` OTA 方案下仍然安全。

### 6.3 什么改动会立刻引入冲突

如果后续有人把 `512K` 项目的 OTA boot 改成 `0x40000`，那么第二固件槽会直接压到当前业务区：

- `event_log` 从 `0x40000` 就开始
- `runtime/soc_kv/cold_kv` 也都位于 `0x40000` 以上

这会造成硬冲突。当前代码已经在布局检查里对 `512K + 非 0x20000 OTA slot` 做了 fail-closed 拒绝，这条保护不能删。

## 7. SDK 顶部保留区

按 `8251/825x` 的 512K 规则，顶部保留区起点是 `0x74000`。这些地址属于 SDK 保留用途，业务区必须避开：

| 项目 | 地址 |
| --- | --- |
| SMP storage 起点 | `0x74000` |
| MAC 地址区 | `0x76000` |
| calibration 区 | `0x77000` |
| master pairing 起点 | `0x78000` |

工程当前正式写入区最高只到 `0x73FFF`，因此没有碰到这部分保留区。

## 8. 当前剩余可用空间

当前 512K 项目里，除去固件槽、OTA 槽、正式业务写入区、迁移兼容区、SDK 顶部保留区，仍有两段可直接规划的新业务空间：

| 空闲区 | 地址范围 | 大小 |
| --- | --- | --- |
| 空闲区 A | `0x48000 ~ 0x4FFFF` | `32K` |
| 空闲区 B | `0x5F000 ~ 0x6FFFF` | `68K` |

合计 `100K`。

另外：

- `0x70000 ~ 0x73FFF` 目前仍保留给旧布局迁移
- 只有在确认所有升级路径都不再依赖旧数据迁移后，才适合回收这一段 `16K`

## 9. 本次检查结论

### 9.1 当前项目无冲突

- 当前正式写入区之间无冲突
- 当前正式写入区与 OTA 区无冲突
- 当前正式写入区与 SDK 顶部保留区无冲突
- 当前正式写入区与旧布局迁移区无冲突

### 9.2 当前项目仍需长期坚持的边界

- 512K 项目 OTA boot 只能保持在 `0x20000`
- `0x78000` 不能重新恢复为业务写入区
- 旧布局迁移区 `0x70000 ~ 0x73FFF` 回收前要先确认升级兼容策略已经结束

## 10. 验证方式

可直接运行：

```powershell
python tc_ble_single_sdk-V3.4.2.8_Patch_0001/tc_ble_single_sdk/vendor/ble_sample/tests_flash_quick_check.py
```

当前脚本会检查：

- 512K 当前布局内部无重叠
- 512K 当前布局不碰 `825x/827x` 保留区
- 512K 当前布局也不碰 `TC321X` 的另一套 512K 保留区定义
- 当前布局与旧布局迁移区不重叠
- `PARAM_ADDR=0x78000` 不在当前正式写入区内
- 当前 `825x_ble_sample.bin` 小于默认 OTA 124K 上限
- `param.c` 中历史 `PARAM_ADDR` 路径保持只读兼容，不会再直接写该地址
