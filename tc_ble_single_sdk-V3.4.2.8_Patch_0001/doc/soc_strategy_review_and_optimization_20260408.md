# SOC 模块梳理与策略优化说明

日期：`2026-04-08`

## 1. 模块职责与当前调用链

当前工程里，`SOC` 主链路集中在 `vendor/ble_sample`：

- `sh367309_datadeal.c`
  - `App_AFEGet()` 读取 AFE 实时数据
  - 更新 `g_stCellInfoReport.u16VCellMax/u16VCellMin/u16VCellDelta`
  - 更新 `g_stCellInfoReport.u16Ichg/u16IDischg`
- `SocEnhance.c`
  - `soc_param_lib_init()` 从 `soc_kv_store` 恢复 `soc/dsg/cycle`
  - `APP_SOC_IntEnhance_Ctrl()` 做运行态 `SOC` 计算
  - `SOC_Result_Pass()` 把结果同步到 `g_stCellInfoReport.SocElement`
- `app.c`
  - 启动阶段初始化 AFE、恢复 `soc_kv`
  - 主循环每 `200ms` 调一次 `APP_SOC_IntEnhance_Ctrl()`
  - 主循环尾部调用 `soc_kv_store_update_and_log_if_changed()` 做掉电保持

所以从系统工程视角，`SOC` 实际是三层结构：

1. AFE 输入层：电压、电流、温度
2. 估算层：积分、校正、端点收敛
3. 输出/持久化层：上报显示、Modbus/BLE、Flash 保持

## 2. 原实现的主要问题

### 2.1 有效策略基本只剩积分

虽然代码里有端点修正、OCV 校正、满充/空电钳位的历史逻辑，但当前真正持续生效的主要是：

- 充电时按 `u16Ichg` 积分
- 放电时按 `u16IDischg` 积分

这会导致：

- 静置很久后，`SOC` 仍强依赖上次保存值
- 长期漂移后缺少温和回归真实电压区间的机制
- 满充/空电边界容易出现“接近但不到位”的体验

### 2.2 启动恢复缺少合理性校验

原启动流程是：

1. 读取 `soc_kv`
2. 直接 `soc_param_lib_init(&d)`
3. 后续才逐步更新 AFE 数据

如果热区保存值和当前电芯静置电压明显不一致，启动后会先显示一个“历史 SOC”，对用户来说容易产生：

- 掉电重启后 `SOC` 明显不合理
- 换电芯/异常恢复后 `SOC` 不贴近真实状态

### 2.3 输入边界保护不足

原实现对以下输入缺少统一约束：

- `set_soc_param()` 外部写入的 `soc`
- `soc_kv_store` 恢复出来的 `soc/dsg/cycle`

风险包括：

- 非法 `SOC > 100`
- `dsg` 超范围导致循环统计异常
- `cycle` 异常值进入 `SOH` 计算

### 2.4 状态切换处存在计数器下溢风险

`SOC_Cont_AH_Int_CHG()` / `SOC_Cont_AH_Int_DSG()` 原先在退出积分态时，直接对 `uint8_t` 计数器做 `--`：

- 当计数已经是 `0` 时会发生下溢
- 会造成短时状态抖动后的节拍异常

这类问题不一定每次都显性暴露，但属于典型的“偶发体验差、难复现”风险。

## 3. 本次优化策略

本次优化遵循三个原则：

- 不改变现有对外接口
- 优先做低风险、可解释、可长期维护的策略增强
- 对 e-bike 仪表场景优先保证“开机显示稳定”，避免中段 `SOC` 上电跳变

### 3.1 启动前增加一次 AFE 快照

在 `app.c` 启动阶段，恢复 `soc_kv` 前先调用一次：

```c
App_AFEGet();
```

目的：

- 先拿到一帧 `VCell/Ichg/IDischg`
- 给 `SOC` 启动合理性判断提供输入

这样后续 `soc_param_lib_init()` 进入运行态时，`SOC` 模块已经具备最基本的电压上下文。

### 3.2 增加运行态输入限幅

在 `SocEnhance.c` 内增加统一约束：

- `SOC` 限幅到 `0~100`
- `DSG` 限幅到 `0~79`
- `cycle` 限幅到 `0~65535`

作用：

- 防止异常 Flash 值、外部写值把运行态拉到非法区间
- 保证 `SOH` 计算输入始终可控
- 保证 Modbus/BLE 上报值稳定

### 3.3 增加启动 OCV 合理性校正

新增“启动一次性 OCV 校正”策略：

- 仅在“静置且电压样本有效”时执行
- 用 `VCellMin/VCellMax` 的保守加权值估算一个 OCV `SOC`
- 仅在“明显空电端点”或“明显满电端点”时做硬校正
  - `ocv_soc == 0` 且电芯已落到空电区
  - `ocv_soc == 100` 且电芯已进入满电区
- 中段 `SOC` 启动时不按 OCV 直接拉回

设计意图：

- 启动时优先修正“明显错到端点”的历史值
- 对 e-bike 仪表保留中段显示连续性，避免用户一开机就看到 `SOC` 跳几格

### 3.4 增加静置缓慢跟踪

新增“静置 OCV 慢跟踪”策略：

- 仅在：
  - `Ichg == 0`
  - `IDischg == 0`
  - 电压样本有效
  - 单体压差不过大
  时生效
- 先连续稳定 `5` 分钟
- 之后每 `30` 秒最多只调 `1%`
- 若 OCV 估算值与当前 `SOC` 差距小于 `8%`，则不动作

这样能兼顾两件事：

- 长时间静置后，`SOC` 会逐步回归更合理值
- 不会出现用户看到的“静置一会儿突然跳 8%~15%”

### 3.5 增加端点同步钳位

新增满充/空电端点同步：

- 满充条件：
  - 充电状态
  - `VCellMax >= SOC_100_VAL`
  - `VCellMin` 也已经接近满电区间
  - 持续若干周期
- 空电条件：
  - 静置状态
  - `VCellMin <= SOC_0_VAL`
  - `VCellMax` 也已落入低电区间
  - 持续若干周期

达到条件后：

- 直接把 `SOC` 钳到 `100%` 或 `0%`
- 同时清空积分残量

这解决的是典型体验问题：

- 满充停在 `97%~99%`
- 空电后仍显示 `3%~5%`

### 3.6 修正积分态切换的下溢问题

对 `s_u8_CHG200msCnt` / `s_u8_DSG200msCnt` 做了保护：

- 只有计数器大于 `0` 才允许 `--`

这让充放电状态在临界抖动时更稳，避免积分节拍异常。

## 4. 本次修改的工程效果

从用户体验角度，优化后的行为预期是：

1. 重启后中段 `SOC` 以延续上次显示为主，不会因为启动校准突然跳几格
2. 满充更容易收敛到 `100%`
3. 长时间静置后，`SOC` 会以很小步长慢慢修正，而不是突然大跳
4. 不会因为异常写值或坏数据把 `SOC` 拉到非法范围
5. 临界电流抖动场景下，`SOC` 状态切换更稳定
6. 只有在明显满电/空电端点，启动时才会把历史 `SOC` 快速纠正到正确端点

从维护角度，新的策略实现仍然保持：

- 计算逻辑集中在 `SocEnhance.c`
- AFE 输入层不改接口
- 持久化层不改协议、不改地址、不改 Flash 格式

## 7. 建议的实机验证项

建议至少做以下几组板级验证：

1. 上电恢复
   - 先让板子静置在中等电量
   - 断电重启
   - 观察仪表 `SOC` 是否基本延续上次显示，不出现中段明显跳变

2. 满充收敛
   - 持续充电到单体高压区
   - 观察 `SOC` 是否最终稳定到 `100%`

3. 静置慢校正
   - 让板子经历一段充/放电后进入静置
   - 观察 `SOC` 是否在约 `5` 分钟后才开始小步长回归，且每次只变动 `1%`

4. 空电端点
   - 放电到低压区后静置
   - 观察 `SOC` 是否能收敛到 `0%`

5. 外部写值鲁棒性
   - 通过 `0x1005` 写入边界值和异常值
   - 确认 `SOC` 最终不会超出 `0~100`

## 8. 当前仍保留的风险

本次没有做的内容：

- 没有引入更细粒度的电芯 OCV 查表
- 没有做温度补偿 OCV
- 没有重构成“真实 SOC / 显示 SOC”双层模型
- 没有调整 `soc_kv` 默认 `dsg/cycle` 口径

所以后续如果你要继续抬高策略上限，推荐下一步演进方向是：

1. 引入分化学体系的 OCV 查表
2. 区分 `raw_soc` 与 `display_soc`
3. 将满充学习、空电学习、静置学习拆成独立状态机
4. 统一 `SOC` 默认参数的文档口径与代码口径
