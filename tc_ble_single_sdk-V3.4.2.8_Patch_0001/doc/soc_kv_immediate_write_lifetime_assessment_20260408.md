# soc_kv 变化即写寿命评估

日期：`2026-04-08`

## 1. 本次结论

`soc_kv_store_update_and_log_if_changed()` 已改成：

- `soc / dsg / cycle` 任意变化即调用 `soc_kv_store_write_all()`

同时，`soc_kv_store_write_all()` 走 `flash_kv32_write_pairs()`，底层会先比对 cache：

- 如果值和当前 cache 完全一样，不会真的写 flash
- 只有至少一个 key 变化时，才会产生一次真实事务写入

所以当前语义是：

- 值不变：不写
- 任意一个值变了：写一次

## 2. 计算前提

### 2.1 当前项目口径

- 平台：`8251 / 512K`
- `soc_kv` 分区：`8 sector`
- sector 大小：`4KB`
- `SOC` 粒度：`u8SOC_Now`，`0~100` 整数百分比
- 当前默认容量：`100Ah`
- 你给定的工况：
  - 放电电流：`10A`
  - 充电电流：`2A`

### 2.2 事务大小

`soc_kv` 只保存 3 个 key：

- `SOC`
- `DSG`
- `cycle`

`flash_kv32` 单次 3-key 事务大小：

- sector header：`32B`
- tx header：`16B`
- item：`3 * 8B = 24B`
- commit：`4B`
- 单次事务总长：`44B`

sector 可用区为 `4096 - 32 = 4064B`，因此：

- 单 sector 可容纳 `floor(4064 / 44) = 92` 次事务
- `8 sector` 环形下，单个 sector 再次被擦除前，全局约可承载 `736` 次事务

## 3. 写入频率估算

对于 `C(Ah)` 容量、`I(A)` 电流，若 `SOC` 以 `1%` 粒度变化：

- `1%` 容量对应 `0.01 * C Ah`
- 单次 `1%` 变化时间约为 `0.01 * C / I` 小时
- 每天写入次数约为：

```text
writes_per_day = 24 / (0.01 * C / I) = 2400 * I / C
```

当前默认 `C = 100Ah`：

### 3.1 10A 持续放电

- `1%` 变化时间：`1Ah / 10A = 0.1h = 6 分钟`
- 写入次数：约 `240` 次/天

说明：

- 放电过程中 `u8SOC_Now` 会按 `1%` 下降
- `u8DSG_SOC_Int` 也按累计放电百分比变化
- `cycle` 每累计 `80%` 放电增加一次
- 这三者即使一起变，也只产生一次事务写入，不是 3 次

### 3.2 2A 持续充电

- `1%` 变化时间：`1Ah / 2A = 0.5h = 30 分钟`
- 写入次数：约 `48` 次/天

充电时主要是 `SOC` 变化，`DSG` 与 `cycle` 一般不会比它更快。

## 4. 擦除频率与寿命

单个 sector 的擦除频率：

```text
erase_per_day = writes_per_day / 736
```

理论寿命：

```text
lifetime_days = 100000 / erase_per_day
```

计算结果：

| 场景 | 写入/天 | 单 sector 擦除/天 | `100k P/E` 理论寿命 | `10k P/E` 理论寿命 |
| --- | --- | --- | --- | --- |
| `10A` 持续放电 | `240` | `0.326` | 约 `840` 年 | 约 `84` 年 |
| `2A` 持续充电 | `48` | `0.065` | 约 `4201` 年 | 约 `420` 年 |

## 5. 对容量变化的缩放公式

如果后续不是 `100Ah`，可直接按下面公式缩放：

```text
writes_per_day = 2400 * I / C
erase_per_day = writes_per_day / 736
lifetime_years_100k = 84.02 * C / I
```

举例：

- `58Ah`、`10A`：理论寿命约 `487` 年
- `104Ah`、`10A`：理论寿命约 `874` 年
- `270Ah`、`10A`：理论寿命约 `2268` 年

## 6. 风险边界

上面的结论依赖两个前提：

1. `SOC` 仍然是 `1%` 级整数变化，不是高频细粒度抖动值
2. `flash_kv32` 的 key 数仍然是当前 `3` 个，`8 sector` 布局不变

如果后续改成：

- 更细的 `SOC` 分辨率
- 更高频的滤波前原始值直接持久化
- 更小的分区

那就需要重新算寿命。

## 7. 最终判断

在当前项目、当前容量默认值和你给的 `10A / 2A` 工况下：

- 把 `soc_kv` 改成“变化即写”是可以接受的
- 当前寿命不是瓶颈
- 真正需要继续防范的是后续有人把持久化对象改成更高频、更细粒度的变量
