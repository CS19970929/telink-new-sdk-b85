# 8251 / 512K Flash 模块寿命与简化评估

## 1. 范围与结论

本文按当前项目 `8251` 系列、`512K flash` 布局分析当前所有业务 Flash 模块的理论寿命、稳定性和可合并性，覆盖：

- `soc_kv`
- `bms_cold_kv_store`
- `runtime`
- `bms_event_log`
- `btname`
- 旧布局兼容区与 OTA 边界

直接结论如下：

- 当前项目不存在 Flash 地址冲突，当前正式写入区与 OTA、SDK 保留区不重叠。
- 当前真正需要重点关注的不是“分区不够”，而是“写入策略是否合理”。
- `cold_kv`、`runtime`、`event_log` 从寿命角度都满足正常使用。
- `btname` 从寿命角度满足正常使用，但掉电原子性最差，是当前最弱的一环。
- `soc_kv` 的物理分区已经够用，但当前工作区代码把刷写条件改成了“`soc/dsg/cycle` 三者同时变化才写”，寿命当然充裕，但会引入持久化遗漏风险；这不是正确的寿命优化方式。
- 如果后续要“简化和合并”，最适合合并的是 `btname -> cold_kv`；最不建议做的是把 `hot kv`、`cold kv`、`runtime`、`event_log` 直接物理合并到同一块写入池。

## 2. 评估前提

### 2.1 当前 512K 布局

当前项目 512K 正式写入区如下：

| 模块 | 地址范围 | 大小 |
| --- | --- | --- |
| `event_log` | `0x40000 ~ 0x47FFF` | `32K` |
| `btname` | `0x50000 ~ 0x50FFF` | `4K` |
| `runtime` | `0x51000 ~ 0x52FFF` | `8K` |
| `soc_kv` | `0x53000 ~ 0x5AFFF` | `32K` |
| `cold_kv` | `0x5B000 ~ 0x5EFFF` | `16K` |

迁移兼容区：

| 模块 | 地址范围 | 用途 |
| --- | --- | --- |
| 旧 `soc_kv` | `0x70000 ~ 0x71FFF` | 升级迁移来源区 |
| 旧 `cold_kv` | `0x72000 ~ 0x73FFF` | 升级迁移来源区 |

SDK 顶部保留区：

- `0x74000 ~ 0x7FFFF`

### 2.2 寿命口径

理论寿命按单个 sector 的擦除寿命估算。

本文默认使用：

- `4KB` sector
- `100k` 次擦除寿命/sector 作为主口径

说明：

- `100k` 是用于工程估算的保守主口径，不等于已经确认当前实物 Flash MID 一定是 `100k P/E`
- 如果实物只支持 `50k`，本文年限减半
- 如果实物只支持 `10k`，本文年限除以 `10`

换算公式：

```text
实际寿命 = 文中寿命 * (实物 P/E / 100000)
```

## 3. 各模块写入模型

### 3.1 flash_kv32 通用模型

`soc_kv` 和 `cold_kv` 都基于 `flash_kv32`。

该模型的关键参数：

- sector header = `32B`
- 单条事务长度 = `20 + 8 * item_count`
- 写满当前 active sector 后，compact 到下一个 sector，并擦除旧 sector

因此，判断寿命时需要看：

- 单次事务包含多少个 key
- 一共分配了多少个 sector

### 3.2 runtime 模型

`runtime` 不是 KV，而是固定长度 append log：

- 单条记录 `16B`
- `2` 个 sector
- 每次写一条记录
- 用满当前 sector 后切到另一 sector，并擦除即将写入的 sector

### 3.3 event_log 模型

`event_log` 也不是 KV，而是快照环形日志：

- 单条快照 `224B`
- `8` 个 sector
- 每发生一次事件，就写一整条快照
- 一个 sector 放满后切到下一 sector

### 3.4 btname 模型

`btname` 是最简单的一类：

- 独占 `1` 个 sector
- 每次修改都整 sector 擦除后重写
- 没有双副本，也没有 append log

## 4. 理论寿命分析

### 4.1 soc_kv

#### 当前结构

- key 数量：`3`
- 单次整包写入：`44B`
- 分区：`8` 个 sector，共 `32KB`

按 `flash_kv32` 模型可得：

- 每个 sector 在一次生命周期内可承载约 `92` 次 `3-key` 更新
- 同一个 sector 再次被擦除前，整个模块大约可承载 `736` 次 `3-key` 更新

换算结果：

| 热点写频率 | 单个 sector 擦除频率 | 100k P/E 理论寿命 |
| --- | --- | --- |
| `1 次/分钟` | `1440 / 736 = 1.96` 次/天 | 约 `140` 年 |
| `1 次/5秒` | `17280 / 736 = 23.48` 次/天 | 约 `11.7` 年 |
| `1 次/秒` | `86400 / 736 = 117.39` 次/天 | 约 `2.33` 年 |

#### 当前工作区实际情况

当前工作区里，`soc_kv_store_update_and_log_if_changed()` 被改成了只有 `soc/dsg/cycle` 三者同时变化才写：

- [soc_kv_store.c](/D:/telink/tc_ble_single_sdk-V3.4.2.8_Patch_0001%20(1)/tc_ble_single_sdk-V3.4.2.8_Patch_0001%20(1)/tc_ble_single_sdk-V3.4.2.8_Patch_0001/tc_ble_single_sdk/vendor/ble_sample/soc_kv_store.c:268)

这会导致：

- 寿命看起来非常充裕
- 但大量本应持久化的变化不会落盘

所以对 `soc_kv` 的结论是：

- 从“物理寿命”看，目前 8 sector 已经足够
- 从“功能正确性”看，当前工作区刷写条件有明显风险，不能把“少写了”当成寿命优化成果

#### 结论

- 只要热数据落盘被限制在 `5s` 级或更慢，当前 `8 sector` 是够用的
- 如果恢复成 `1s` 级连续落盘，寿命会明显缩短，不建议
- 当前剩余问题是写入策略回归，不是分区不够

### 4.2 cold_kv

#### 当前结构

- 总 key 数量：`78`
- 其中保护参数 `65` 个
- system 参数 `8` 个
- control 参数 `5` 个
- 分区：`4` 个 sector，共 `16KB`

对应事务长度：

| 写入类型 | key 数 | 单次事务长度 |
| --- | --- | --- |
| `set_protect()` | `65` | `540B` |
| `set_system()` | `8` | `84B` |
| 单个 `control` / 单个 `system value` | `1` | `28B` |
| compact 全量快照 | `78` | `644B` |

#### 最坏情况 1：整包保护参数频繁写

这是 `SaveParam()` 路径，当前 `0x06` 单寄存器写保护参数时就会触发。

按当前结构可得：

- 每个 sector 生命周期内大约能承载 `7` 次整包 `protect` 更新
- 同一个 sector 再次被擦除前，整个模块大约可承载 `28` 次整包 `protect` 更新

换算结果：

| 整包保护参数写频率 | 单个 sector 擦除频率 | 100k P/E 理论寿命 |
| --- | --- | --- |
| `10 次/天` | `10 / 28 = 0.36` 次/天 | 约 `767` 年 |
| `100 次/天` | `100 / 28 = 3.57` 次/天 | 约 `76.7` 年 |
| `1000 次/天` | `1000 / 28 = 35.71` 次/天 | 约 `7.67` 年 |

一个更接近现场的风险点是：

- 如果上位机用 `0x06` 逐项写完 65 个寄存器
- 那么一次调参会触发约 `65` 次 `SaveParam()`
- 这相当于一次调参就消耗约 `65 / 28 = 2.32` 次单个 sector 擦除预算

这不是“马上写坏”，但说明：

- `0x06` 连续逐项调参非常不经济
- 现场工具应优先走 `0x10` 批量写

#### 最坏情况 2：system / control 高频写

这类写入量要小得多：

- `set_system()` 单次 `84B`
- 单 key `28B`

在当前 `4 sector` 布局下，这两类寿命都远高于保护参数整包写，不是主要瓶颈。

#### 结论

- `cold_kv` 寿命满足正常使用
- 风险不在“分区太小”，而在“上位机如果大量走 `0x06` 单寄存器写，会产生不必要写放大”
- 当前 `4 sector` 配置已经基本够用

### 4.3 runtime

#### 当前结构

- 单条记录：`16B`
- `2` 个 sector，共 `8KB`
- 每个 sector 可存 `256` 条
- 整个模块在同一个 sector 再次被擦除前，可承载约 `512` 次保存

当前工作区参数：

- 保存周期：`1` 分钟
- [runtime.c](/D:/telink/tc_ble_single_sdk-V3.4.2.8_Patch_0001%20(1)/tc_ble_single_sdk-V3.4.2.8_Patch_0001%20(1)/tc_ble_single_sdk-V3.4.2.8_Patch_0001/tc_ble_single_sdk/vendor/ble_sample/runtime.c:10)
- 工厂模式时长：`18` 小时
- [runtime.h](/D:/telink/tc_ble_single_sdk-V3.4.2.8_Patch_0001%20(1)/tc_ble_single_sdk-V3.4.2.8_Patch_0001%20(1)/tc_ble_single_sdk-V3.4.2.8_Patch_0001/tc_ble_single_sdk/vendor/ble_sample/runtime.h:7)

理论换算：

| 写入场景 | 单个 sector 擦除频率 | 100k P/E 理论寿命 |
| --- | --- | --- |
| 连续 `1 次/分钟` 永久运行 | `1440 / 512 = 2.81` 次/天 | 约 `97.4` 年 |
| 连续 `1 次/10分钟` 永久运行 | `144 / 512 = 0.28` 次/天 | 约 `974` 年 |

更贴近当前产品的实际口径：

- 一次完整 `18h` 工厂计时周期约写 `1080` 次
- 相当于每个 sector 大约消耗 `1080 / 512 = 2.11` 次擦除预算
- 即使每天做一次“完整 runtime 清零再跑满 18h”的极端测试，也有约 `47407` 次完整测试周期预算

#### 结论

- `runtime` 当前寿命完全满足使用
- 当前更大的问题不是寿命，而是功能策略：升级时是否真的要清零 runtime
- 这个模块没有必要并入其他 KV 区

### 4.4 event_log

#### 当前结构

- 单条快照：`224B`
- 每个 sector 可存 `18` 条
- `8` 个 sector 共 `144` 条
- 同一个 sector 再次被擦除前，整个模块大约可承载 `144` 次事件落盘

换算结果：

| 事件写入频率 | 单个 sector 擦除频率 | 100k P/E 理论寿命 |
| --- | --- | --- |
| `10 次/天` | `10 / 144 = 0.07` 次/天 | 约 `3945` 年 |
| `100 次/天` | `100 / 144 = 0.69` 次/天 | 约 `394` 年 |
| `1000 次/天` | `1000 / 144 = 6.94` 次/天 | 约 `39.4` 年 |

#### 结论

- `event_log` 的寿命非常充裕
- 当前 8 sector 已明显足够
- 没必要为寿命再额外扩大分区

### 4.5 btname

#### 当前结构

- 独占 `1` 个 sector
- 每次改名都先擦后写
- 当前记录体积不到 `32B`
- 没有 wear leveling

换算结果：

| 改名频率 | 单个 sector 擦除频率 | 100k P/E 理论寿命 |
| --- | --- | --- |
| `1 次/天` | `1` 次/天 | 约 `274` 年 |
| `10 次/天` | `10` 次/天 | 约 `27.4` 年 |
| `100 次/天` | `100` 次/天 | 约 `2.74` 年 |

#### 结论

- 从寿命角度，`btname` 对正常使用完全够用
- 但它是当前所有 Flash 模块里掉电原子性最差的

## 5. 稳定性与异常断电分析

### 5.1 已经比较稳的模块

下面这些模块都采用了“正文先写，commit 最后写”或同等级别的校验机制：

- `soc_kv`
- `cold_kv`
- `runtime`
- `event_log`

再配合 [flash_store_safe.h](/D:/telink/tc_ble_single_sdk-V3.4.2.8_Patch_0001%20(1)/tc_ble_single_sdk-V3.4.2.8_Patch_0001%20(1)/tc_ble_single_sdk-V3.4.2.8_Patch_0001/tc_ble_single_sdk/vendor/ble_sample/flash_store_safe.h) 的：

- 写后读回校验
- 擦后全 `0xFF` 校验
- Flash lock / unlock 封装

所以极端断电下，这几类模块通常只会丢“最后一条未提交写入”，不容易破坏上一条已提交数据。

### 5.2 当前最弱的模块

`btname` 仍然是：

- 先擦 sector
- 再整包写新值

见：

- [btname_modbus.c](/D:/telink/tc_ble_single_sdk-V3.4.2.8_Patch_0001%20(1)/tc_ble_single_sdk-V3.4.2.8_Patch_0001%20(1)/tc_ble_single_sdk-V3.4.2.8_Patch_0001/tc_ble_single_sdk/vendor/ble_sample/btname_modbus.c:202)

因此在最坏情况下：

- 改名过程中掉电
- 会导致该 sector 变成无效状态
- 下次启动大概率退回默认名，而不是保留旧名

这不是系统级致命故障，但确实是当前稳定性最弱的一块。

### 5.3 当前工作区额外风险

当前工作区 `soc_kv` 刷写条件被改成：

- 只有 `soc/dsg/cycle` 三个值都变化才落盘
- [soc_kv_store.c](/D:/telink/tc_ble_single_sdk-V3.4.2.8_Patch_0001%20(1)/tc_ble_single_sdk-V3.4.2.8_Patch_0001%20(1)/tc_ble_single_sdk-V3.4.2.8_Patch_0001/tc_ble_single_sdk/vendor/ble_sample/soc_kv_store.c:281)

这会导致：

- 寿命变好只是表面现象
- 实际问题是大量更新根本没存进去

这属于持久化正确性风险，不属于分区寿命不足。

## 6. 是否满足使用

按当前 `8251 / 512K` 项目和 `100k P/E` 主口径判断：

| 模块 | 寿命是否满足正常使用 | 主要问题 |
| --- | --- | --- |
| `soc_kv` | `满足` | 当前工作区刷写条件回归，存在“该写不写”风险 |
| `cold_kv` | `满足` | `0x06` 连续单寄存器调参会产生较大写放大 |
| `runtime` | `满足` | 主要是策略问题，不是寿命问题 |
| `event_log` | `满足` | 寿命裕量很大 |
| `btname` | `满足` | 寿命够，但掉电原子性不足 |

如果按非常悲观的 `10k P/E` 估算：

- `cold_kv`、`runtime`、`event_log`、`btname` 仍然基本能满足正常现场使用
- `soc_kv` 若恢复成“近似 `1次/秒` 连续写”就不满足
- `soc_kv` 若控制在 `5s` 级及以下，一般仍可接受，但寿命裕量会明显变窄

## 7. 是否建议合并或简化

### 7.1 不建议物理合并的模块

#### 不建议把 `soc_kv` 和 `cold_kv` 合并成一个 KV 池

原因：

- `soc_kv` 是热数据，写频率高
- `cold_kv` 是冷配置，写频率低
- 两者合并后，热数据会拖着冷数据一起参与 compact
- 这样会把冷配置寿命、异常恢复范围和调试复杂度一起放大

结论：

- 两者继续分区是对的
- 现在已经共享 `flash_kv32` 引擎，代码层面并不重复，没必要为了“看起来只有一个模块”去物理合并

#### 不建议把 `runtime` 合并进 `cold_kv`

原因：

- `runtime` 的写入模式是 append log
- `cold_kv` 的写入模式是 KV 事务
- `runtime` 单独分离后，掉电恢复和工厂清零都更简单
- 合并后会把“分钟级计时”写入频率耦合到配置区

结论：

- `runtime` 保持独立更稳

#### 不建议把 `event_log` 合并进 KV

原因：

- `event_log` 是明显的大对象快照环形日志
- 合并进 KV 后，compact 代价和实现复杂度都会上升

结论：

- `event_log` 应继续独立

### 7.2 建议合并的模块

#### 建议考虑把 `btname` 并入 `cold_kv`

这是当前最值得合并的一项。

原因：

- `btname` 是低频配置，天然属于 cold data
- 当前 `btname` 自己维护单 sector 原始格式，掉电原子性最差
- 如果并入 `cold_kv`，可以直接继承：
  - CRC
  - commit
  - 多 sector wear leveling
  - 统一迁移逻辑

代价：

- 需要把名字拆成若干 `u32` key，或扩展一个小型 blob-kv 能力

结论：

- 如果只做一个“简化且提升稳定性”的合并动作，优先做 `btname -> cold_kv`

### 7.3 建议做“代码层抽象”，但不建议“物理池合并”

当前代码里真正可以简化的是：

- `runtime`
- `event_log`

这两个模块都属于“固定记录 + CRC + commit + 环形切换”的 append-log 模型。

建议：

- 保持分区独立
- 但代码层可以抽出一个通用 `flash_append_log` helper

这样得到的好处：

- 减少重复手写的 raw flash 状态机
- 不牺牲寿命隔离
- 不牺牲掉电恢复可控性

## 8. 建议优先级

### P1

- 修正当前 `soc_kv` 刷写条件回归，不要用“三个字段必须同时变化”来代替节流

### P2

- 如果要做一个最有收益的简化，优先把 `btname` 合并进 `cold_kv`

### P3

- 保留 `soc_kv` / `cold_kv` / `runtime` / `event_log` 四类物理分区，不建议为了表面统一而强行合并

### P4

- 上位机调参尽量优先走 `0x10` 批量写，避免 `0x06` 连续逐项写保护参数

## 9. 最终结论

当前 `8251 / 512K` 项目从 Flash 寿命角度看：

- 整体是满足使用的
- 目前没有哪个模块因为分区太小而“必然不够用”

当前最值得你真正处理的不是“继续扩大分区”，而是：

- 修正 `soc_kv` 当前工作区的刷写策略回归
- 评估是否把 `btname` 合并到 `cold_kv`
- 保持 hot / cold / runtime / event_log 四类数据的独立寿命池，不要盲目合并

一句话总结：

- `分区总体够用`
- `寿命总体够用`
- `真正的剩余风险点是 hot kv 写入条件错误和 btname 掉电非原子`
