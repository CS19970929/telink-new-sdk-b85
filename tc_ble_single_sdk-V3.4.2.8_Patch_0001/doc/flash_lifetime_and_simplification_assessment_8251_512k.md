# 8251 / 512K Flash 寿命与简化评估

## 1. 结论

按当前 `8251 / 512K` 布局和当前代码策略，项目各 flash 模块理论寿命满足正常使用。

当前更重要的结论是：

- 当前不存在正式分区冲突
- `soc_kv` 即使改成“任意变化即写”，在当前 `8 sector` 布局下寿命仍然满足使用
- `cold_kv`、`runtime`、`event_log` 理论寿命余量都比较充足
- `btname` 已并入 `cold_kv`，不再是单 sector 擦写弱点
- 不建议把 `soc_kv`、`cold_kv`、`runtime`、`event_log` 再物理合并到同一块写入池

## 2. 评估前提

- sector 大小按 `4KB`
- NOR Flash 擦除寿命按 `100k P/E` 保守估算
- 当前正式分区：
  - `event_log`: `0x40000 ~ 0x47FFF`，8 sector
  - `runtime`: `0x51000 ~ 0x52FFF`，2 sector
  - `soc_kv`: `0x53000 ~ 0x5AFFF`，8 sector
  - `cold_kv`: `0x5B000 ~ 0x5EFFF`，4 sector

## 3. 各模块寿命分析

### 3.1 soc_kv

当前写入策略：

- `soc / dsg / cycle` 任意变化即写
- 分区大小 `8 sector`

当前 `flash_kv32` 下，`soc_kv` 单次 3-key 事务长度为：

- sector header: `32B`
- tx header: `16B`
- 3 个 item: `3 * 8B = 24B`
- commit: `4B`
- 单次事务合计：`44B`

每个 sector 可承载约 `92` 次 3-key 事务；`8 sector` 环形下，单个 sector 再次被擦除前，全局大约可承载 `736` 次事务。

在当前默认容量 `100Ah` 下，若 `SOC` 以 `1%` 步进变化：

- `10A` 持续放电：`1%` 约每 `6` 分钟变化一次，约 `240` 次写入/天
- `2A` 持续充电：`1%` 约每 `30` 分钟变化一次，约 `48` 次写入/天

对应寿命估算：

| 场景 | 写入次数/天 | 单个 sector 擦除/天 | `100k P/E` 理论寿命 |
| --- | --- | --- | --- |
| `10A` 持续放电 | `240` | `240 / 736 = 0.326` | 约 `840` 年 |
| `2A` 持续充电 | `48` | `48 / 736 = 0.065` | 约 `4201` 年 |

因此这里可以直接下结论：在你给的 `10A` 放电、`2A` 充电口径下，`soc_kv` 改成“变化即写”仍然远在安全区间内。

### 3.2 cold_kv

当前 `cold_kv` 保存的是低频配置：

- 保护参数
- 系统参数
- 控制 epoch
- 蓝牙名 suffix

其典型写入来自：

- 上位机改保护参数
- 升级 epoch 首次落盘
- 低频蓝牙名配置

即使按相对激进的“每天几十次整包保存保护参数”估算，4 sector 轮转寿命仍然足够。当前 `cold_kv` 的主要问题不是寿命，而是现场是否滥用 `0x06` 单寄存器逐项配置，这会带来不必要的写放大。

### 3.3 runtime

当前 `runtime` 使用：

- `2 sector`
- `16B` 记录
- `1 min` 一次落盘

按每分钟保存计算：

- 每天 `1440` 次记录写入
- 单个 sector 每天约 `2.8` 次擦除
- 理论寿命约 `97` 年

所以当前 `1 min` 周期从寿命上是安全的。它更偏向“减少掉电损失时间”，而不是 flash 风险点。

### 3.4 event_log

当前 `event_log` 使用：

- `8 sector`
- `224B` snapshot
- 异常事件/开机/睡眠时才追加

这类日志不是高频周期性写入，寿命余量很大。当前需要关注的是事件触发策略和异常掉电一致性，而不是分区大小不足。

### 3.5 btname

`btname` 已并入 `cold_kv`，寿命模型等同于低频配置项。

相比旧方案，当前收益是：

- 不再单独擦整个 sector
- 和 `cold_kv` 共用 CRC / commit / wear leveling
- 异常断电时更不容易破坏上一次已提交值

## 4. 简化与合并建议

### 4.1 已完成的简化

- 删除旧布局迁移逻辑
- `btname` 并入 `cold_kv`
- 清理 `flash_store_cfg.h` 中已失效的迁移 getter
- 清理若干头文件中的死宏定义

### 4.2 不建议继续做的合并

不建议把以下模块物理合并成一个通用写入池：

- `soc_kv`
- `cold_kv`
- `runtime`
- `event_log`

原因很直接：

- 写频率不同
- 故障恢复语义不同
- 热数据会拖累冷数据寿命
- 调试和问题定位会更差

### 4.3 推荐的结构

保留当前四块正式持久化区：

- `event_log`
- `runtime`
- `soc_kv`
- `cold_kv`

这已经是当前项目在寿命、稳定性和实现复杂度之间比较平衡的方案。

## 5. 剩余风险

- `soc_kv` 当前“变化即写”依赖 `SOC` 仍然是 `1%` 级步进；如果后续改成更细粒度高频抖动值，寿命模型要重算
- `runtime` 当前配置 `FW_UPGRADE_RESET_RUNTIME_EPOCH = 1u`，意味着下一次升级会重置 runtime；这是产品策略风险，不是 flash 寿命风险
- 保护参数如果长期通过 `0x06` 单寄存器逐项改写，会产生明显写放大
- 目前完成的是静态复核与脚本验证，还没有覆盖完整 TC32 编译和真机断电注入
