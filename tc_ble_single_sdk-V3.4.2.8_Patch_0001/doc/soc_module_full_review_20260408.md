# SOC 模块完整梳理与后续优化建议

日期：`2026-04-08`

## 1. 文档目的

本文针对当前工程中的 `SOC` 模块做一次完整梳理，目标有三项：

- 说明 `SOC` 模块当前的职责边界、调用链和核心数据流
- 明确现有策略真正生效的部分、已经落地的优化、仍保留的风险
- 给出后续可执行的优化方向，并区分“可低风险马上做”和“需要实机验证后再做”

本文面向后续维护、产品讨论、调参和板级验证，尽量避免只描述局部函数行为。

## 2. 模块范围与文件边界

当前 `SOC` 相关逻辑主要分布在以下文件：

### 2.1 核心计算层

- `vendor/ble_sample/SocEnhance.c`
  - `SOC_Calculate_Element` 运行态核心数据
  - `APP_SOC_IntEnhance_Ctrl()` 主状态机入口
  - 充放电安时积分
  - 启动校正、静置慢跟踪、端点同步
- `vendor/ble_sample/SocEnhance.h`
  - `SOC_CALCULATE_ELEMENT` 结构定义
  - 对外接口声明

### 2.2 输入采样层

- `vendor/ble_sample/sh367309_datadeal.c`
  - `App_AFEGet()` 读取 AFE 寄存器
  - `DataLoad_CellVolt()` / `DataLoad_Current()` 更新电压电流
  - 写入 `g_stCellInfoReport`
- `vendor/ble_sample/sci_upper.h`
  - `g_stCellInfoReport` 的数据结构定义
  - `SocElement` 是上层显示和通信统一出口

### 2.3 启动与调度层

- `vendor/ble_sample/app.c`
  - 启动阶段先取 AFE 快照，再恢复 `soc_kv`
  - 主循环每 `200ms` 执行一次 `APP_SOC_IntEnhance_Ctrl()`
  - 主循环尾部调用 `soc_kv_store_update_and_log_if_changed()`

### 2.4 持久化层

- `vendor/ble_sample/soc_kv_store.c/.h`
  - 保存 `soc / dsg / cycle`
  - 从 hot KV 恢复运行态
  - 通过 `flash_kv32` 内部 cache 提供运行态读值

### 2.5 外部接口层

- `vendor/ble_sample/modbus_rtu.c`
  - `0x1005` 可直接调用 `set_soc_param()`
  - `0x2319` 可写循环次数
- `vendor/ble_sample/sif_send.c`
  - 通过 `g_stCellInfoReport.SocElement.u16Soc` 上报给 BLE / 仪表侧

从系统工程角度，`SOC` 实际是四层：

1. 采样层：AFE -> `g_stCellInfoReport`
2. 估算层：`SocEnhance.c`
3. 持久化层：`soc_kv_store`
4. 输出层：`SocElement` / Modbus / BLE / 仪表

## 3. 核心数据结构

### 3.1 内部运行态：`SOC_Calculate_Element`

核心字段含义如下：

- `u8SOC_Now`
  - 当前内部 `SOC`
- `u32CapNow`
  - 当前剩余容量，单位为内部累计容量单位
- `u32CapFull`
  - 当前满充容量，已叠加 `SOH`
- `u32CapFactory`
  - 出厂额定容量
- `u32CapChange`
  - 当前积分残量
- `u8DSG_SOC_Int`
  - 放电累计量，用于折算循环次数
- `u32Cycle_times`
  - 循环次数
- `soh`
  - 当前 `SOH`

### 3.2 对外出口：`g_stCellInfoReport.SocElement`

该结构是整个系统读取 `SOC` 的统一窗口：

- `u16Soc`
- `u16Soh`
- `u16CapacityNow`
- `u16CapacityFull`
- `u16CapacityFactory`
- `u16Cycle_times`

也就是说，仪表、BLE、私有协议、寄存器读值看到的 `SOC`，最终都来自这里。

## 4. 启动链路

当前启动时序是：

1. `AFE_Reset()` / `AFE_IsReady()` / `SH367309_UpdataAfeConfig()`
2. `App_AFEGet()`
3. `soc_kv_store_init()`
4. `soc_kv_store_get()`
5. `soc_param_lib_init(&d)`

这意味着当前已经不是“盲恢复历史值”，而是：

- 启动前先拿一帧实时电压、电流
- 再恢复历史 `soc/dsg/cycle`
- 然后让 `SocEnhance.c` 在已有电压上下文下完成启动合理性判断

这对 e-bike 仪表体验很关键，因为它避免了模块在完全没有电压上下文时就把历史 `SOC` 直接推给上层显示。

## 5. 运行时调度节拍

### 5.1 当前真实节拍

运行时存在两个不同节拍：

- `APP_SOC_IntEnhance_Ctrl()`：每 `200ms`
- `App_AFEGet()`：每 `1s`

所以当前实现虽然有 `200ms` 状态机，但从输入侧看，本质上仍是：

- 每 `1s` 获得一个新的电流/电压样本
- `200ms` 状态机负责防抖、切换和积分触发
- 充放电积分每累计 `5` 个 `200ms` 周期后，才按当前样本折算一次容量变化

因此它本质是“按秒积分、按 `200ms` 做状态切换防抖”的架构。

### 5.2 这一架构的含义

优点：

- 节拍清楚
- 计算量小
- 与当前 `u16Ichg/u16IDischg` 的单位折算是自洽的

限制：

- 电流快速变化时，`SOC` 响应分辨率只有 `1s`
- 充放电状态切换可能比实际变化滞后最多约 `1s`
- 静置判断也依赖 `1s` 采样刷新

这不一定是 bug，但必须在设计文档里明确，否则后续维护容易误以为这是“真正按 `200ms` 实时积分”。

## 6. 当前 `SOC` 计算逻辑

### 6.1 主状态机

`APP_SOC_IntEnhance_Ctrl()` 只做两类事：

1. 根据 `SOC_Cali_Flag` 跑主状态机
   - `SOC_CALI_STATE_TRANSFER`
   - `SOC_CALI_CONT_CHG`
   - `SOC_CALI_CONT_DSG`
2. 每轮再执行策略层
   - `soc_apply_startup_ocv_correction()`
   - `soc_apply_terminal_sync()`
   - `soc_apply_idle_ocv_tracking()`

最后通过 `SOC_Result_Pass()` 把结果写回 `g_stCellInfoReport.SocElement`。

### 6.2 充电积分

在 `SOC_Cont_AH_Int_CHG()` 中：

- `u16Ichg >= SOC_VIRTUAL_CURRENT_CHG` 才认为进入充电态
- 连续若干周期满足后，打开 `u8CHG_AHCalcu_Flag`
- 每次触发后：
  - `u32CapChange += Ichg`
  - `u32CapNow += Ichg`
  - 按 `u32CapFull` 折算出应增加的 `SOC`

这个实现属于典型的安时积分法。

### 6.3 放电积分

在 `SOC_Cont_AH_Int_DSG()` 中：

- `u16IDischg >= SOC_VIRTUAL_CURRENT_DSG` 才认为进入放电态
- 连续若干周期满足后，打开 `u8DSG_AHCalcu_Flag`
- 每次触发后：
  - `u32CapChange += IDischg`
  - `u32CapNow -= IDischg`
  - 按 `u32CapFull` 折算出应减少的 `SOC`
- 同时把放电量累积到 `u8DSG_SOC_Int`
  - 达到阈值后累计为一次循环

### 6.4 `SOH` 计算

当前 `SOH` 不是基于容量学习，而是基于循环次数的分段线性近似：

- `0~80` 次：`SOH = 100`
- `81~500` 次：`100 -> 90`
- `501~799` 次：`90 -> 80`
- `>=800` 次：钳到 `80`

这是一套简化模型，优点是实现简单、不会抖动；缺点是不能体现真实老化差异。

## 7. 当前已生效的策略增强

### 7.1 输入限幅

当前已经对以下运行态做统一约束：

- `SOC 0~100`
- `DSG 0~79`
- `cycle 0~65535`

目的：

- 防止热区脏值
- 防止外部写入越界
- 保证 `SOH` 和容量计算不会进入异常区

### 7.2 启动端点校正

启动阶段采用“电压有效 + 静置 + 仅端点硬校正”的策略：

- 中段 `SOC` 不在启动时直接拉回
- 明显空电时才纠到 `0%`
- 明显满电时才纠到 `100%`

这是针对 e-bike 仪表体验做的偏保守设计，目标是：

- 减少开机跳变
- 避免用户看到中段 `SOC` 一上电就跳几格

### 7.3 静置慢跟踪

当前静置跟踪规则是：

- 先静置约 `5` 分钟
- 若 OCV 估算与当前 `SOC` 偏差至少 `8%`
- 之后每 `30` 秒最多调整 `1%`

这属于“温和回归”机制，不是“静置即重算”。

### 7.4 满充 / 空电端点同步

当前增加了端点钳位：

- 满充持续满足条件后直接收敛到 `100%`
- 空电持续满足条件后直接收敛到 `0%`

它解决的是用户最容易感知的体验问题：

- 明明充满了却卡在 `97%~99%`
- 明明已经到底了还剩几格

### 7.5 充放电切换防抖

当前状态切换里已经修掉 `uint8_t` 计数器下溢问题，并保留了：

- 连续判定
- 转态延时
- 小电流阈值

这让充放电边界抖动时更稳。

## 8. 当前精度与体验的真实水平

### 8.1 结论

当前 `SOC` 实现已经可以满足“可用且体验不差”的量产级基线，但还不是“高精度电量估算”。

更准确地说，它的定位是：

- 主体靠安时积分
- 辅以端点和静置修正
- 明显偏向显示稳定和工程可控

### 8.2 为什么它现在足够适合 e-bike 仪表

对 e-bike 用户来说，最重要的不是实验室意义上的绝对精度，而是：

- 开机不乱跳
- 满充能到 `100%`
- 低电能到 `0%`
- 行驶过程中变化基本连续
- 静置后不会突然大跳

当前策略正是围绕这些点做的。

### 8.3 当前精度上限来自哪里

限制主要有四类：

- `OCV` 估算仍是简化线性映射，不是按化学体系查表
- 温度没有进入 `OCV-SOC` 补偿
- 当前积分仍以 `1s` 样本为主，不是更高频实时积分
- 没有区分“内部真实 `SOC`”和“显示 `SOC`”

## 9. 已确认的剩余问题

### 9.1 `OCV` 模型仍然过粗

当前 `soc_estimate_percent_from_cell_mv()` 实质上是：

- `SOC_0_VAL -> 0%`
- `SOC_100_VAL -> 100%`
- 中间做线性映射

它适合作为辅助修正，不适合作为高精度主估算器。

### 9.2 编译时硬编码仍覆盖参数化入口

`SocEnhance.c` 当前启用的是固定：

- `SOC_100_VAL = 4180`
- `SOC_0_VAL = 3100`

虽然源码里保留了从参数区读取 `u16Soc_V_100 / u16Soc_V_0` 的路径，但当前编译分支没有启用。

这意味着：

- 当前不同项目的 `SOC` 电压阈值不够灵活
- 后续若更换电芯体系，需要改代码而不是调参数

### 9.3 `SOC` 和显示值仍是同一个量

当前上层显示直接使用 `g_stCellInfoReport.SocElement.u16Soc`，而这个值就是内部 `u8SOC_Now`。

这意味着：

- 内部校正一旦发生，上层看到的也是同一个值
- 还没有单独的“仪表平滑显示层”

对 e-bike 这种强显示场景，长期看更合理的做法是：

- `real_soc` 负责估算
- `display_soc` 负责限速变化和用户观感

### 9.4 AFE 采样与 `SOC` 状态机节拍不一致

当前不是实时高频采样，而是：

- `SOC` 状态机：`200ms`
- AFE 刷新：`1s`

这会带来：

- 电流突变时响应较慢
- 行驶中快速负载变化只能按秒级修正

这不是必须立刻改，但属于下一阶段优化重点。

## 10. 本次新增的低风险优化

### 10.1 重新确认 hot KV 读路径实际已缓存

本轮梳理里专门确认了 `soc_kv_store_update_and_log_if_changed()` 的读路径。

表面上看，主循环尾部每次都会先 `soc_kv_store_get()` 再决定是否写入，容易让人误以为：

- 每轮都要读一次 Flash
- 这会成为 `SOC` 运行时的额外存储负担

但继续下钻到底层后可以看到：

- `soc_kv_store_get()` 最终调用的是 `flash_kv32_get()`
- `flash_kv32_get()` 直接返回 `kv->cache[key_index].value`
- 也就是说，运行态读值本身已经是 RAM cache，不是每次都重新扫 Flash

结论：

- 当前 hot KV 读路径已经足够轻量
- 没必要再在 `soc_kv_store` 上额外包一层重复缓存
- 真正值得优化的重点仍然是 `SOC` 策略本身，而不是这段持久化读路径

## 11. 后续优化建议

### 11.1 P1：参数化 `SOC_0_VAL / SOC_100_VAL`

建议将当前固定阈值恢复为可配置参数，并明确来源：

- 优先使用参数区
- 没有配置时再回退默认值

收益：

- 不同电芯体系更容易适配
- 量产调参不需要改源码

风险：

- 需要确认参数区已有值的单位和初始化流程

### 11.2 P1：引入分化学体系 OCV 查表

当前头文件已保留化学体系枚举，说明架构上曾考虑过这条路。

建议：

- 三元、磷酸铁锂分别建立 `OCV-SOC` 表
- 静置修正和启动端点判定统一走查表结果

收益：

- 中低电量区间更准确
- 端点判定鲁棒性更高

风险：

- 需要结合实测数据标定

### 11.3 P1：拆分 `real_soc` 与 `display_soc`

建议增加双轨：

- `real_soc`
  - 供内部计算、端点学习、保护逻辑使用
- `display_soc`
  - 供仪表、BLE 显示使用
  - 增加变化速率限制和抖动抑制

这会比现在“直接把内部值推给仪表”更适合 e-bike。

### 11.4 P2：提升 AFE 输入刷新节拍

建议评估两种方案：

- 方案 A：`App_AFEGet()` 提升到 `200ms`
- 方案 B：保持 `1s` 读取，但显式把积分定义为“按秒积分”，避免误读

如果 I2C / 功耗允许，方案 A 的体验会更好；如果成本敏感，至少要把方案 B 写进设计说明。

### 11.5 P2：端点学习独立状态机

建议将以下逻辑彻底拆开：

- 满充学习
- 空电学习
- 静置学习

不要都混在一个轻量策略函数里，而是分别管理：

- 进入条件
- 持续时间
- 退出条件
- 修正步长

这样后续维护和调参会明显更清楚。

## 12. 是否建议继续马上改

我的判断分两类：

### 12.1 建议现在就做

- 文档化当前节拍和状态机语义
- 参数化 `SOC_0_VAL / SOC_100_VAL`
- 补充板测验证矩阵
- 若系统开销敏感，保留并继续完善 `soc_kv_store` RAM 缓存

### 12.2 不建议在没有板测前直接大改

- 直接把 AFE 刷新提到 `200ms`
- 直接把 OCV 逻辑切成复杂查表
- 直接引入大幅显示平滑逻辑

原因：

- 这三类改动都可能改变仪表动态体验
- 没有实车路测和静置数据，很容易“理论更好，体感更差”

## 13. 推荐验证矩阵

建议至少验证以下工况：

1. 中段冷启动
   - 断电前记录仪表 `SOC`
   - 冷启动后确认是否基本延续显示

2. 满充收敛
   - 观察是否能稳定到 `100%`
   - 观察停止充电后是否不会立刻掉格

3. 低电收敛
   - 放到低电区后静置
   - 观察是否能到 `0%`

4. 长静置自放电
   - 中段电量静置若干小时
   - 观察 `SOC` 是否只做慢修正而不是大跳

5. 动态负载切换
   - 模拟 e-bike 上坡、平路、空载切换
   - 观察 `SOC` 是否连续、是否有异常回弹

## 14. 总结

当前 `SOC` 模块已经从“几乎只有积分”进化为“积分主导 + 启动合理性判断 + 静置慢修正 + 端点同步”的组合策略，已经明显更适合 e-bike 仪表场景。

但从长期维护和精度上限看，后续最值得做的不是继续堆更多 if-else，而是沿着三个方向演进：

- 参数化
- 查表化
- 显示层与内部估算分层

如果按投入产出比排序，下一阶段最值得优先推进的是：

1. 参数化电压阈值
2. 双轨 `real_soc/display_soc`
3. 分化学体系 OCV 查表
